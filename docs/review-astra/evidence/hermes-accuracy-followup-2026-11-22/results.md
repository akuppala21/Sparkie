# Research accuracy on the local Huihui model

These are first attempts at individual owner questions using the same one-Spark Huihui model. Each ordinary turn used the native Hermes agent with its usual research and workspace tools. The structured comparison used the native schema and fixed excerpts. A normal chat, a structured answer and a test of a file reader measure different behaviors.

The broader rewrite stayed out of the application. An original can settle a specific question and still be insufficient for a different claim in the same answer. The manual research rubric now covers both the context-extension and memory-overhead errors encountered here. The recovery fixture also checks that the assistant gives the supported procedure even when the requested deadline cannot be established.

The package and runtime conditions matter for the p-queue result. Its v8.1.0 implementation handles a timeout by resolving to `undefined` under the default settings. It starts the timer after the task is dequeued. Cancellation of underlying work depends on the supplied work and its timeout wrapper. ## Reading a named file at the requested revision

Skill 1.6.1 used the new file reader in an ordinary version-specific question. It recovered from a missing path, located the tagged TypeScript source, and read the implementation and README. Its two requested answers were correct. It then repeated the unsupported claim that work always continues after a timeout. It completed in 178.1 seconds. The reader retrieved the relevant original and the assistant still overstated what that original established. [Publisher's file](https://github.com/sindresorhus/p-queue/blob/v8.1.0/source/index.ts)

Skill 1.6.2 asks for a short answer to each requested fact and evidence before adding a claim about another component or version. On the same p-queue question, it answered both parts correctly and made no unsupported cancellation claim. It read the tagged README through the helper and obtained the tagged implementation with the native terminal. It did not use the helper's new named-file option for that second read. It reached the final answer in 91.6 seconds over eight model requests, compared with 192.4 seconds for 1.6. This is a targeted regression result. One run per version does not establish a typical response time.

On the separate public Python question, both 1.6.1 and 1.6.2 reached 480 seconds without a final answer. The 1.6.1 run retrieved both release-specific library manuals. The 1.6.2 run used 17 model requests, wandered into patch-release security details and consulted a floating library page from a different release. The dependency question improved while the open-ended manual lookup remained unreliable.

The two original instructions also handled some questions without a change. On the build-record control, both correctly withheld a cross-job comparison and calculated a measured within-job change from 180 to 126 seconds, a 30% reduction. On a simple arithmetic question, both returned the correct answer in one model request with zero research tools.

## Measuring and remembering a result

In the original Cedar Glass benchmark, Sparkie made seven requests and called the comparison verified. With a helper that recorded all eight required requests, it then ran the correct batch but spent the rest of its time writing a long skill and never delivered the answer. That skill save failed. A new chat found the numbers in the project and falsely claimed the skill existed.

The new implementation uses a native Hermes skill for a requested local serving measurement. Its client records the actual request, response, whole-request wall time and prompt-cache counters. A short instruction routes measurements to that skill. When the owner asks for later recall, the agent saves the project name and receipt location through native Hermes memory. All sample data stays in the project. Routine conversation has no additional model or tool call mandated by this feature.

On a second synthetic project, Harbor Loom, Sparkie initially bypassed the client, sent an extra probe and wrote a new measurement script. The revised routing led it to open the skill first and run exactly eight requests. It returned the correct medians in 75.4 seconds and a fresh chat recovered them in 34.7 seconds. Its first answer still called all eight prompt tokens reused. The engine reported eight reused and one processed. That observation led to the final client adding the processed and total counts while retaining support for older receipts.

On the final Cedar Glass run, the upstream server recorded exactly eight generation jobs. All eight completions matched. From three timed requests per setting, the whole-request medians were 2.904372 ms with caching off and 2.083554 ms with it on. Each timed request had ten input tokens. With caching on, the engine reused nine and processed one. The owner answer reported those facts in 259.3 seconds. A fresh session reopened the project receipt and gave the same numbers in 28.6 seconds. It expressed unnecessary uncertainty about the timing scope. The client times the complete request through reading the response. These measurements apply to the repeated prompt on the tiny CPU fixture. ## Release decision

Research6 passed 137 affected tests on the compute Spark in 9.00 seconds. Eight of the nine local model behavior cases passed in the sealed package. On a failed stop, Sparkie correctly reported that the workload still ran and made no additional dispatch, but wrapped its required JSON in a Markdown code fence. The strict parser rejected the reply. Separately, the structured research case satisfied its schema and still promoted a title's million-token context claim beyond the supplied setup. The source showed a 262,144-token configured window. Research6 is staged privately. These results support using the checked measurement and recall changes in the research branch. The full live rollout remains on hold.
