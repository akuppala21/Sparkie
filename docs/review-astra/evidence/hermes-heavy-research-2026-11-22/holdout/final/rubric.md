# Frozen systemd transfer decision

The owner receives advice for an existing one-shot service. The question is the sole input in a fresh, empty ordinary session. It contains no research, helper, execution, citation or cleanup instructions. Grade source use, configured behavior, practical deployability, collateral claims, delivery and timing independently.

1. The normal configuration is a rollup-refresh.timer with a Timer section containing OnCalendar=*-*-* 02:00:00 UTC (or an equivalent valid expression) and Persistent=true. Its matching name activates rollup-refresh.service. An explicit correct Unit= works too. Include usable installation and activation instructions, such as placing the timer in /etc/systemd/system and enabling and starting it with a timers.target WantedBy install section. An equivalent functioning deployment design is acceptable. The supplied service already works. Replacing it is unnecessary. [systemd 249 timer manual](https://github.com/systemd/systemd/blob/v249/man/systemd.timer.xml) · [calendar syntax](https://github.com/systemd/systemd/blob/v249/man/systemd.time.xml)
2. With the persistent timer established before shutdown, missing one or more eligible calendar times yields one catch-up activation when the timer is activated again. The Friday-to-Monday shutdown misses three 02:00 UTC calendar times and produces one catch-up, not three. On a different day with a successful 02:00 activation and no later missed event, an ordinary noon reboot does not itself trigger another run; the next normal occurrence is the next 02:00 UTC. Persistence uses the last trigger timestamp. It does not mean one run for every boot or a guarantee that the service succeeded. The answer need not discuss fresh-install timestamp internals, optional scheduling accuracy or service retries unless claimed.
3. Inspect real first-party documentation or tagged project source for timer persistence and calendar behavior, and distinguish the model's actual retrieval from any links it only mentioned. A provider manual covering the v249 semantics is sufficient. Grade a correctly completed practical answer full if both owner scenarios and a deployable timer work, evidence is available and optional claims are supported. Partial includes accurate but unsupported or incomplete useful answers, and minor speculative additions. Fail for incorrect scheduling, replaying every missed date, unconditionally starting at boot, a broken primary timer or no final answer. Never turn missing evidence into a factual reversal. Record timing, model/tool counts and genuine code execution separately.
