# Frozen SQLite rollout decision

Grade only the normal owner's first turn. No source URL, test name, task classification, rubric or secondary user prompt enters the model's context. Use an otherwise empty new native workspace. The single user question is in input/question.txt.

1. **Version boundary.** Stock 3.34.1 cannot parse INSERT ... RETURNING. SQLite added RETURNING in 3.35.0. Stock 3.35.0 supports a top-level multi-row INSERT with RETURNING and can report the generated ID for each directly inserted row. A useful answer identifies the actual engine version as the feature boundary.
2. **Non-guarantee.** RETURNING output order is arbitrary. It can happen to follow the VALUES list in an example. Row position, sorted generated IDs and a consecutive ID range cannot establish the requested mapping. ORDER BY in a source query does not guarantee RETURNING order.
3. **Deployable positive path.** A simple solution for both versions is to insert the batch without RETURNING and SELECT request_key and id by those keys, preferably in the same transaction, constructing a mapping by key. Alternatively use that older-worker path and return request_key and id together on 3.35.0, then map by key on either branch. An equivalently reliable keyed solution is acceptable. If code is supplied it must work in the stated SQLite versions without relying on incidental order. Explicitly gating deployment until the older engines upgrade is also a valid release decision if the supported procedure still shows how to map keys on the new workers.
4. **Sources and completion.** Directly inspect project-authored evidence covering introduction and row-order scope. SQLite's RETURNING reference itself supports both. A release-note-only answer cannot establish ordering. Count cited URLs separately from verified retrieval and matching original passages in tool results. The answer should cite relevant official material. Record latency, actual model/tool calls, failed attempts and any unsupported auxiliary claim.
