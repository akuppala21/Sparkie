WHAT IT DOES
(a) A Hugging Face repo started by its full name joins Recipes (added-models.json, through the existing `addModel`) once its download worked; the same job then looks its setups up (`refreshSetups` with wait, which calls `startDig`) and starts with `bestHow`. (b) `find_setups` adds such a repo instead of its 404. (c) The look gains a fifth source, read last: the model's own card on Hugging Face (code blocks only), using the unused `dig.codeBlocks`/`findServe`/`fromText`.

1. service/dig.mjs, after `fromText` (~line 406). New pure export:
```js
// A model's own card (its README.md on Hugging Face): the engine commands in its code blocks that serve this very repo.
// Only code blocks are read, never the card's words. At most 6 a card; a command of over 60 words, or with a word
// over 300 characters, is skipped.
export function fromCard(text, repo) {
  const out = [], seen = new Set(), own = String(repo || '').toLowerCase();
  if (!own) return out;
  for (const block of codeBlocks(String(text || '').slice(0, 400000))) {
    const hit = findServe(block);
    if (!hit || String(hit.model || '').split(':')[0].toLowerCase() !== own) continue;
    if (hit.args.length > 60 || hit.args.some(a => String(a).length > 300)) continue;
    const key = JSON.stringify([hit.engine, hit.image || null, hit.args]);
    if (seen.has(key)) continue;
    seen.add(key);
    out.push({ ...fromText(hit, { url: `https://huggingface.co/${repo}`, author: String(repo).split('/')[0], date: null, kind: 'model-card', credibility: 'medium', notes: 'From the model’s own card on Hugging Face' }), repo });
    if (out.length >= 6) break;
  }
  return out;
}
```
(credibility must be 'medium': `recipeCatalog` hides 'low'. `SOURCE_RANK` already has 'model-card': 5, so it sorts last; it carries no speed, so `bestHow` puts any measured setup first.)

GUARDS THAT MUST HOLD
- Who can cause a join: only the existing gate. The asker's words name `org/name` in full, or the yes on the question (kept server-side, once, 15 minutes). A look-only key cannot (changes are refused before the action runs).
- Join only after the download worked (start), or after the repo is re-read on Hugging Face by code (`addModel`). Never from a search result.
- A failed join never fails a start. Nothing new starts, stops, claims or runs on a Spark; nothing on Spark 2; no SSH, Tailscale, firewall or access change.
- Card text is data: only code-block commands for that very repo are parsed; no card words reach the brain; flags, env and image pass `dig.vetSetup` at save and `resolveHow` at use (R27); a setup that lets the model run its own code is still never picked by `bestHow` and still refused by `start_model`.

=== risk
1. Joining Recipes widens what that model may do later, with no further question: run across two Sparks (those parts run with more privileges for the cable), start on an app's call at /v1, and a daily look. The gate is the existing one, so an agent the owner lets change things can cause a join by taking the yes, as it can already cause the download.
2. A model card is written by whoever uploaded the model. Its command becomes one-click after the same checks as every other source (flag and env lists, an approved image pinned by digest or Spark Console's own, never the model's own code by itself). A poor but allowed command can still become the only "best" setup for a new model; a failed start then goes through the known fixes and put-back. Owner decision already implied by keeping A9: the maker's card is trusted, ranked last.
3. start_model, start_model_across and find_setups all get new versions (startModel, digModel, both actions' text change). After install each needs a new lock and one validation run on the real Sparks; until then an agent's plain call gets the validation question.
4. The first start of a new model waits a little longer before it claims its Spark: one more Hugging Face read (up to 20 s) and the look (existing bound, 150 s; on a cold cache it may not finish, and the start then uses the engine's defaults while the setups land for next time).
5. Gated models: the card cannot be read without signing in, so it counts as no card (no token is ever sent).
6. A saved-workflow step `find_setups` on a repo outside Recipes now stops with "needs an answer first" instead of a 404; either way the step fails.
7. The dig fixture now holds two kinds of entry; a fixture card that names an image tag would make the test reach a registry.
8. Not checked by running: I read the code only. The full download-then-start path has no completing test today (the existing one is paused midway), so B1 may surface stand-in gaps the builder has to fix in the test, not in the rails.
