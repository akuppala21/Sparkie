# R56

## Rule

**R56.** Asleep, and waking for work (contract 9.22 and 9.28; it carries on from R41, which is full). A start that
names no Spark wakes the Sparks it needs and no more: one for a model that fits on one Spark (R41, `wakeOne`), both
for a model that runs only across two. How many it needs is read from what the start already knows, never guessed:
for a model on the disk of a Spark that is on, its own need as `plan()` reckons it (`wakeNeedOf`: its `spark.json`'s
`memoryGiB`, else its size and 15%), against a sleeping Spark's recorded `memTotal` less the 8 GB kept free; for a
model to download, the recipe's versions (`sparks`, `needGB`; a version for two counts by half its need on each).
Only a model that may run across two is woken for in pairs (`wakeMayPair`: from Recipes, not a draft, an engine that
pairs). Its partner is the other end of a cable between two compute Sparks that passed its test (`wakePartner`),
never a cable to the hub. A record that lists the model is woken with its partner when its memory less 8 GB can't
hold the model's need and the partner is asleep too. With no record listing it: the first whose disk and memory hold
the whole model, else the first that holds half of it, with its partner when that one is asleep; with none of these,
nothing is woken and the answer says why. A model whose files are only on sleeping Sparks has no known need before
the wake: the start is placed again once that Spark is on, and when the live look then shows that no compute Spark
that is on holds its need alone (`wakeNeedsTwo`), it wakes once more (its partner, by the same records) and never
again; a model that fits on one Spark is never woken for twice. The start's context counts its wakes (`poweredOn`).
The start a wake hands over to carries its own workflow version (`powerThen`), so its lesson has its start code (R48)
and counts with the same start's failures without a wake. The run is still counted once, on the power-on operation,
under the workflow the start ran: `start_model_across` when Spark Console placed it across two (`ranAs`, handed up from
a power-on inside it), so such a start validates the two-Spark workflow, never `start_model`. A saved workflow's run
knows what a start through any number of wakes started (`startedBy` follows every operation handed over to), so it
stops that model at a workload's end, after a failure or a cancel, and after a restart. A start that fails puts back a
job it stopped only through the job folder check (R38), in the same command as its `docker start` (`putBack`).
After a wake, a download's version is picked from the live look at the Sparks that just came on (`wakeLiveStatus`:
their free memory and disk as the start's own look reads them), never from the cached status, which the status loop
takes every 30 s and so can be from before they came on (it found no room on them, and the start ended "no version
fits" with the Sparks on). The wake chain (`offHolds`, `powerThenStart`, `powerThen`, `powerOnSparks`, `powerOnOne`,
`bringBackParked` and the helpers above) is on the start workflows' code list, so a change to it is a new start
version. The hub and its plug are never woken or switched (R41).

A Spark Spark Console powered off reads asleep (D4). Its mark (`powerMark`: each Spark's `offOnPurpose` in
`fleet_status`, `poweredOff` in `/status`) carries `asleep`, the look's own sentence from its record (`asleepView`:
"Spark 4 is asleep since <time> UTC; N models on its disk then. A look doesn't wake it."), and that `/status` node has
`asleep: true` while it doesn't answer. The fleet notes Sparkie is sent say "asleep, on purpose (not a fault)". The
installer's reach check reads `power.json` (one it can't read, or a record that isn't one, counts as none): a Spark
with a record that doesn't answer is "asleep (Spark Console powered it off at …)", not "NOT reachable"; it prints of
the file's text only what can be printed. A record that carries a problem (a wake that failed) is never asleep: the
mark's `asleep` is null, `/status` has `asleep: false`, and the notes and the installer say the problem instead. A
record that isn't one (a `power.json` edited by hand) is passed over by every reader (`powerState`) and left out at the
next save. A planned sleep or wake carries `planned: true`: `spark-offline` for a Spark with a record; `spark-online`
while its record is there, a power operation runs on it, or after a `spark-powered-on` since it went dark
(`plannedWake`; that event is written only when Spark Console turns on a Spark it had a record for). `lastOnOff` counts
neither, so a crash after a planned wake is restarted at once (R19); a Spark that goes dark by itself after one is an
outage as before.
A box Spark Console has open on a Spark (R62: on record, labelled with its own name) is its own, never "started outside
Spark Console". An asked power-off says it is open, whose it is and what its folder holds, and ends it with its folder
inside the operation, before anything is parked (`powerBoxesEnd`); a box of a chat whose task is under way is the
owner's question first, and the yes ends it (a power-off an agent asks is the owner's question anyway, naming it). A box
that comes while models are parked stops the power-off, as anything else does. The idle power-off counts a box as use.
A container named and labelled like a box that is not on record (one from before a restart, or opening now) refuses
the power-off in words that say so; it ends at its own time.

## Why

The after-landing review of D5 (2026-11-14): a model that runs only across two Sparks, started with no Spark named,
had one Spark woken, or none, and was refused for memory while its partner slept; and a start that woke a Spark left
a lesson with no start code, which B3's passing-over never matches.

## Today

- Status remembers which completed power-off operation preceded each probe. A confirmed cut replaces an older
  cached online reading in `/status` and `fleet_status`, even if that probe or another Spark finishes late, or the
  plug cache still says on. A probe started after the cut can prove the Spark came back. This uses operation ids,
  not wall-clock order; old power records with no completed-cut id keep their existing status behavior. Both start
  workflows hash this status path: `pickVersion` reads it before a wake.
- A model whose files are only on sleeping Sparks is woken for one Spark at a time (two boots, one after the other),
  not both at once: a recipe's version for two on a sleeping record isn't read before the wake.
- `power_on` of a Spark shut down by hand (no record) writes no `spark-powered-on`: its return is planned only when
  the look sees it on while the operation still runs; otherwise a crash after it is held half an hour, as before D4.
- For up to a minute after a sleeping Spark is turned on by hand (five after a restart of Spark Console), until the
  power round ends its record, its mark in `/status` still says "is asleep since …", beside `asleep: false`.
