# R52

## Rule

**R52.** The rail (contract 3.11; the one page, milestone 5 and section 7, item 13): a change Sparkie asks for runs at
once only while its brain is *checked*; otherwise it is one button, as an unclear change is (`propose`). The check is in
`runAction` (16-actions.mjs) for every call made through Sparkie's chat (the page, Telegram, the agent door's
`ask_sparkie`, a carry-on turn), so no way around the chat loop skips it; a lookup never meets it, but opening a box
does (`run {on: "box"}` is a change: `boxRun` asks it for Sparkie's call itself, R62); the owner's own press, call or
command does not. Checked (`brainRail`) means all of: the chat goes to Sparkie's own model (not routed
elsewhere, `POST /main/route`); no start, stop or switch of it is running; this build has a lock naming what its brain
reads (`brainReads`, which holds a page-chat turn and a turn in the paired Telegram chat, each its prompt and tools,
and the fixed words of its other messages, `brainCatalog`'s `words`: the carry-on line, the "Not run" and "Not shown"
notices, the report's lines, the digest's words, the cards and their heading, "Seen before", and what a card and
"Seen before" say was tried and how it failed: `lessonTried`, `lessonFailWords` and the failures' titles) and its case
set (`evalSet`: the version and each case's id and expect, test/lock.mjs); what the model runs can be seen (its
container's image id, and the snapshot of its weights the container loaded: from its own arguments, or the links of
the overlay its start made, `brainRanLook`; a reply and each change wait for that look 3 seconds at most, and a Docker
that hasn't answered by then counts as not checked, which `changes` says); the brain check on record for this exact
brain says checked; and, in that
profile's slot for this mark and set, the newest full run that counts
met the bar, recounted from the record each time (`evalScore`; never a stored flag). A record counts only when it is
well-shaped, of the main set (`setFile` test/eval/cases.json) with every memory addition on, run with no cap, for this
brain's key, holds exactly the lock's case ids with their expects, and carries this console's seal (an HMAC over the
record and its profile's key, with a key kept beside secrets.json, never in the state folder or a copy of it). A partial
run neither gives nor takes; a newer full run that missed the bar takes the pass away. A kept record is never replaced
(the same record again is "already kept"; another with its `at` and build is kept beside it, and of two at one moment
a full run comes before a partial one and one that missed the bar before one that met it, `evalOrder`), `at` is taken
only in the runner's own form, and an entry counts only under its own key (the key computed from the brain serving,
never only the file's). The key a profile and a record belong to (`brainKey`) covers the model, draft, engine, image,
flags, environment, rope settings, how it is asked, the console's own limits for it (`brainLimits`: tool rounds,
changes, `run` calls and tool output a message, the tool cap), its name, and what runs; a record under an older,
narrower key counts for nothing. The loop's limits are the profile's (`turnLimits`, R50): its own while the brain is
checked, else at most 8 rounds and 16 `run` calls a message. A record that could unlock changes (a full run of the main set, no cap, the bar met),
posted while a passkey is set up, is not kept: it waits for the owner's yes (`evalWait`), in memory only, one at a time
(a newer run replaces it and voids its button; a restart forgets it), and only when it is for this build's mark, the
lock's case set and the brain serving now (otherwise 409, nothing kept). The owner gets one owner-only button in their
chat "The brain eval’s result", built by code: the model, engine and image from the console's own record of the setup
serving, never the poster's words; from the record its build, case set, runs against the bar and when; what keeping
it means; that the console can't check the run happened or ran on this brain; and where the post came from. Pressed
on the page with the passkey (`evalYes`) it is kept, sealed, `keptWith` passkey; "No" drops it. Its call is no action
and never reaches Telegram (`PAGE_ONLY`); `sparkie_setup` and `/status` (a needs-you line) say it waits. With no
passkey set up it is kept at once. Any other record is kept and never unlocks. A slot keeps the five newest full
main-set runs and the five newest of the rest, so neither pushes out the other, and the slot this build counts on is
kept first. Unknown is "ask".
A server error, or any answer but 200, 400 or 422, to the brain check's requests keeps nothing; it is never "never
calls a tool". Records the seal's key can't be read for count for nothing, and `changes` says so. `sparkie_setup` says in
one line (`changes`) why Sparkie asks, or that it does not.

## Why

A brain that was never measured on this build, these tools and these cases must not change the Sparks on its own
reading of the owner's words; a stored result that could be typed, edited, moved or outdated must not stand in for one.

## Today

- On the real Sparks, after an install whose mark has no stored passing eval, Sparkie asks before every change until the
  eval has run and the owner pressed its result's button.
- A result that came back with state put back from a copy on the same Spark 2 counts if this console sealed it: the hold
  on what a put-back brings (design E 2.5, P-3) is not built. The seal stops a record being added or changed, not
  removed: whoever can write brain-profiles.json can delete a newer failing run, and an older passing one decides again.
  Nor does it cover the profile: its `outcome` can be edited from not checked to checked beside a sealed pass.
- With rope settings the weights are read from the overlay's links, which the last start of that setup made: a start
  that failed after making them names weights no container loaded.
- For a model kept as a folder (the models folder), the key holds the setup's folder name: nothing of the weights is
  read, and not from the container, so weights changed in place, or another folder given that name, keep the key.
- The rail is the chat's: an agent that asks the same brain through the model address (`/v1`) and makes the changes
  through the agent door, with a key that may change things, meets no rail: those calls are the agent's own.
- `words` hashes the code that writes each fixed line, so a change to the code around a line owes an eval too.
- What the model runs is looked at again for each decision (a reply's limits may use a look 5 seconds old); a chat
  routed elsewhere mid-reply is judged by the route at the moment of the call, not the one the reply began with.
- The run wall that keeps `run` and `write_file` off brain-profiles.json, the seal's key and `api.sock` is not built
  (design A, step 7).
- When the start-up check finds the brain still loading, nothing checks it again by itself; `sparkie_setup` says why
  Sparkie asks, and no needs-you line does.
