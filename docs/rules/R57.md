# R57

## Rule

**R57.** A saved workflow run as a workload (contract 9.27; design D 2.3 as cut): what R35 says of its steps, its job
waits and its clean-up holds; this rule adds what outlives the process. A run keeps a record of itself in
`saved-runs.json` in the state folder (`savedRunKeep`, through `writePrivate`; names, Spark ids and the chat's id, no
secret), rewritten as it goes: its title, the chat that asked, its step count and the step it is at, what its finished
steps started (`started`), what a step under way answered `started` for and is still bringing up (`pending`, a
`restart_model` or `keep_running` step's own container; a start's is known only once its operation ended, so a start
under way is kept as its operation, `starting`), and the Sparks it keeps awake. The record goes when the run ends, however it ends (`savedRunDone`). At start-up the
watcher's one look at operations a restart cut off (`19-watcher.mjs`, its existing one-shot timer) calls
`savedRunsRecover`: for each run still on record, what it started is stopped newest first under the same rules as a
failure (`stopWhatRan`: `keep: true` and "already" left alone, a job only while it still runs; an app cut off before it
joined the list is kept first, so its stop takes it off, only while it is running), the keep-awake holds went with the
old process, one notice says what was stopped, kept or couldn't be stopped (in the chat that asked too), and nothing
is run again. The generic "a restart cut off …, start it again" line is not given for the run's own operation or for
its steps' since it began, but is for a start under way (`savedRunCutOff`; the notice then never says nothing was
running); the operation is still marked interrupted. A change to the file makes no state copy due
(`COPY_IGNORES`).
A job a run starts from its image (`keep_running` with `once` and an image) is handed the one model address in its
settings (`jobModelEnv`, D7; design D 2.4): `SPARK_MODEL_URL`, Spark Console's one address as a container on a compute
Spark sees it (the self-test's, without `/models`); `SPARK_MODEL_NAME`, the model the step's own settings name, else the
one an earlier step of the run started or found running (a start's model, a restarted container's), else `sparkie`;
`SPARK_MODEL_PARALLEL`, for Sparkie its `--max-running-requests` less two, at least 1 (R36 caps app calls at its slots
less one, so one place stays for another app and one for the owner's chat), 1 when the setup doesn't say, and 4 for a
model of the run's own. Settings the step names are kept; only missing ones are added. Sparkie is handed only when its
setup can chat (`can`, `["chat"]` when not said) and answers at least 2 calls at once, or doesn't say how many (then 1);
otherwise the run says why and the job gets none. A job whose container is there already gets none: it runs as it was
made, and the run says so and which model it asks (`jobThere`). None of this touches what a save's yes covers.
`compare_models {workflow, candidates, sample}` (D8; T141) is one operation, `compare`, that runs a saved workflow
with a `model` input once per candidate (1 to 4, the brain first), one after another, as `run_workflow` runs it with
the compare's caller (D6a to D7 hold); those runs are the owner's own unless an agent asked. A candidate's run stops
nothing for room (`noStops`): one that won't start, or fits only if something stops, is listed with why. Its job, made
from its image, gets the compare's suffix (a new container each), `SPARK_SAMPLE` and D7's settings, handed only the
`{model}` step's model, never an `{input}`. Refused by name before anything starts (`compareWontReach`): no job made
from an image, no start of `{model}` before the last job, a job step holding an `{input}` or naming its own
`SPARK_MODEL_NAME` or `SPARK_MODEL_URL`, a step running an old job again by name. The brain's run leaves out the steps
that start, stop or restart `{model}`, and is tried only when its setup can chat and doesn't answer one call at a
time. The score is `result.json` in the folder of the run's last job, read through the worker (no link followed): at
most 4 KB, JSON, written after that job began; only `score` (0 to 1), `ok` and `items` (numbers) are taken, and
nothing else of it is kept or shown. The winner, by code, among runs that ended well with `ok` not false: the best
score leading the next by more than 0.05, every one scored; it is kept (`best`, through `writeSaved`) and a later run
with no model uses it and says so (the brain's view when the brain won; a job made for another model is refused in
those words). Closer, or unscored: the owner picks, from buttons in the chat it was asked in (`compare_models
{workflow, keep}`), or in words; with approvals from Telegram on, its buttons may be pressed there too. Results are
kept (`compared`). One hour in all: at the hour the run under way is cancelled, which stops what it started, and the
best so far is kept or offered. Only the Spark a candidate needs is woken (D5); a look wakes nothing.

A run an agent asked for (its key, its own call through the door, or its chat with Sparkie) is that agent's in each
of its steps (`savedStepAgent`: `agent` and the key's id in the step's context), so every gate that asks an agent asks
in the step as in the agent's own call (a job run again, a GPU app started again, a power-off), and a key removed
during the run stops its next step; the owner's run stays the owner's. The clean-up's stops (`stopWhatRan`, at a bad
end, a workload's good end and after a restart) run as the run, never as the agent: they only take back what this
run's own steps answered `started` for, start and wake nothing, and none asks an agent, so no removed or paused key
leaves leftovers running or a question no one can answer.

What a step started that was on the list of what should be running before that step (held or parked there, so the
step started it again) is stopped by the clean-up like the rest; if that stop takes it off the list, its entry goes
back as it stood just before (`startedListed`, `desiredPutBack`; no revision), marked `putBack`, which self-healing
leaves alone until it next runs. What the owner took off during the run stays off. The result says so ("Still on the
list of what should be running, as before this run: …"), after a restart too.

## Why

A restart in the middle of a workload (an install, a crash) left the model and apps it had started running for nobody,
and the owner was told to start them again.

## Today

- A start step (`start_model`) cut off while its own operation ran isn't stopped: its container is known only when the
  operation ends. Its own cut-off line is still given.
- A Spark that doesn't answer at start-up isn't tried again: what couldn't be stopped there is said in the notice.
- A job's one address is tested on the stand-in fleet only; real use waits on the self-test's sixth line (a container
  reaches the one model address) passing on the real Sparks, the owner's check after the install.
