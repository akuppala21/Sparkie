# R38

## Rule

**R38.** Apps (2026-11-11): `keep_running` alone starts, keeps, restarts or stops a container that is not a model
(`run`: R61, R62). Never on the brain’s Spark, for any verb (`notBrainsSpark` first). Never a console model, a model server
or a protected container, and only the container with exactly that name (`appLook` reads one `docker inspect` and
refuses the start of another container’s id; Docker that didn’t answer is never taken for one that’s gone). A model
server is known by what it is, not by a live probe: Spark Console’s model label, a model engine’s image
(`service/config.json`’s engines and the watcher’s `MODEL_IMAGES`), or the watcher’s record of it as a model; one
Spark Console started as an app (`spark.app=1`) stays an app whatever it answers, and the inventory never lists it as
a model server started outside. A new container gets `spark.app=1` (never `spark.console=1`), a memory cap, named
volumes only, no secret in env or command, ports bound to 127.0.0.1 and the Spark’s tailnet address, and never the
model port; no Docker restart policy, entrypoint, network, IPC or privileges, and no host folder but a job’s two
below. A new image runs at once only for the owner on their tailnet (page, API, the owner’s own Sparkie chat) with the
Spark named and image, port, volumes and env typed as whole words (`appNamed`; the image is checked even when the
watcher knows the name), or a saved step its save covers (R35); otherwise an owner-only button. From an agent (directly, through Sparkie or in a saved step)
or Telegram, keeping, starting, restarting or stopping a container Spark Console didn’t start is an owner-only button
too, and from an agent so is running a job again or starting a stopped GPU app; self-healing, the page and the owner’s
own chat and API act at once. A name that is there with another image, port, volumes or settings than asked is refused
and told what differs, never started as it was; a port that Docker doesn’t publish for it is refused, and any port
above 65535 everywhere. Its ports are read from `docker inspect` (kept for a stopped container), and a recorded port
follows what Docker reports. A new app whose `docker run` fails removes only the container that call made and that
never ran (state `created`). The 8 GB rule holds for every start (the app’s memory figure must fit beyond it;
unreadable memory refuses): a new app’s cap, else a container’s own memory limit, else the owner’s figure
(`memoryGB`); one with none and no figure isn’t started. Done means its container is running and stays running (five
looks, 15 s); its port only decides whether it answers there (any HTTP reply, waited on up to 3 minutes) and so
whether its link is given. Nothing is stopped for not answering (a database is up without a link). One that stops
right after starting is stopped again and kept for its log. It stops nothing to make room. Adopting one that already
runs changes only the list (`keepApp`), no job. A new app under a name still on the list updates its port and memory
figure. A stop while its Spark is off only takes it off the list (`forgetApp`), so it isn’t started at the next
power-on. Healing (`healApp`): at most two bring-backs in six hours, after a crash (exit other than 0, 137, 143) or a
stop seen within five minutes of its Spark coming back on; a clean stop with the Spark on is held; the list is read
again before a bring-back (and by `keep_running` after its look), so a Forget is never undone; a held app’s reason is
its own latest heal event since it last started. Undo leaves app changes alone, except that undoing a model start that
stopped a kept app brings the app back through `keep_running`. Not a workflow (no lock entry or validation). Any
workload (A13, the owner’s decisions of 2026-11-12): `gpu` gives a new app or job the GPU (`--gpus all`,
`--shm-size 2g`, `spark.gpu=1`; `memoryGB` required, up to 112) only on a Spark where no model, model server or other
GPU app runs (`gpuAlone`, checked again with the memory inside the job just before Docker starts it, for a new one
and one that’s there alike, self-healing’s too),
and it stops nothing for room: one GPU thing per Spark, and a model start asks before it stops one (R2). `command` is
the words it runs after the image, each quoted (at most 40, no invisible characters, nothing a mask would hide; a dev
box’s no-password flags pass). `once` makes a job: `spark.job=1` and `spark.chat` (the chat it was asked in), the
shared folder read-only at `/in`, its own `jobs/<name>` there (made first by one fixed `mkdir -p`, `jobFolder`, never
through the worker, whose limit counts jobs’ outputs; it, `jobs` and the shared folder must be real folders, not
links or in one, checked again in the command that runs or starts it) at `/out` with `-w /out`, a port only when
given; no `appUp` and no `ranHere`, so it never joins the list or heals; asked to keep it while it runs answers
`already`; run again (it’s there, stopped) it starts as it was, still off the list, and its watcher row is set
running, so its new end is read
afresh (a look that ran while the row changed leaves it to the next); `do stop` works without a list entry. Its end is
told once by the watcher (`jobEnded`, R23): a notice, and a message in that chat (`tell` too when that chat is
Telegram’s), from its name, exit and times only, never its log. `appNamed` also wants every command word, and with
`gpu` the word and the memory figure; a port only when given. The button says the GPU, the memory figure, the whole
command, and for a job where its files go. A dev box runs with no password by the owner’s choice: a known image kept
with no command (Jupyter Docker Stacks’ `jupyter/…-notebook`, `codercom/code-server`) gets its no-sign-in words
(`start-notebook.py --IdentityProvider.token= --ServerApp.password=`; `--auth none`; `appCommand`), and its answer and
button say anyone on the owner’s tailnet, or the owner signed in anywhere through the app door, can use it only when
its command carries such words (`devBox`), never from the image name alone; its link leads with the door’s when the
door is on (R40). A stack is a saved workflow of `keep_running` steps (no compose, no Docker network); a job step waits for its end (R35). The self-test’s
web page and job are ordinary `keep_running` apps (`spark.app=1`; the job once, with the GPU), from `config.json`’s
`selfTestImage` (a key of its own, not under `images`, so it is never counted as a model engine’s image), with fixed
commands and fixed names `spark-selftest-web-<hash>` and `spark-selftest-job-<hash>` (the hash of what they run). They
stay stopped and are started again by the next self-test. `waitJobEnd` waits for a job’s end: one fixed `docker inspect`
every 10 s through `run`, with a time limit; it changes nothing, and cancelling its operation ends it at once.

## Why

A container is code that runs on a Spark and reaches the tailnet as it; the owner must never be crowded out of memory
or find the hub running more than the brain.
