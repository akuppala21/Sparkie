# R21

## Rule

**R21.** Docker is the truth: scan again before changing (`inventory(null)`, `plan`); caches are for reads. A look
Docker didn’t answer is not a look: the inventory’s and the watcher’s scripts print `docker ok` only when `docker ps`
itself worked. Without it the inventory marks that Spark `dockerOk: false` and the watcher leaves what it knows
untouched (“couldn’t read”, never “nothing there”). Today: only `healReason`, `desiredNow`, `watchHeld`,
`openProblems`, `selfTestPlace`, `powerOnSparks` and `wakeSpark` read the mark; `plan`, `stop_model`, `restart_model`, `running_models`, `container_logs`, `checkSteps`,
placement and `/v1` still see such a Spark as having no containers, stop nothing because of it, and fail at Docker’s
own error.
A saved workflow's clean-up (R35; after a restart, R57) stops only what its own run started, by what Docker says under
the stop's own claim, never by a name alone (A-22). Each item a step started keeps a receipt in `ran` and in
`saved-runs.json` (`startedReceipts`, when the step's operation ended): its Docker id, and for a model or an app the
`since` of its entry on the list of what should be running, for a job (no entry) its start time. `stop_model` and
`keep_running`'s stop, handed the receipt in the call's context (`onlyIf`), look again first (`startedStill`): another
id, start time or `since` means someone started it again since, so it is left, the stop does nothing, and the run's
result says "Left running: … was started again since, not by this run." Such a stop stopped nothing: it is no run of
`stop_model` (`recordWorkflowRun`), and its own line in the chat and on Telegram says it was left running and why,
never "finished" (`postResult`, `tellResultLine`). Every start moves its entry's `since` but self-healing's
(`desiredAfter`); the owner's own ask answered "already" (`start_model`, `restart_model`, `keep_running`; not a run's
step, self-healing or an agent) moves it too (`desiredWish`). The owner's ask while the run's own step is still
starting it (`start_model` answered "already-starting", `alreadyStarting`; a restart or keep answered "already",
`desiredWish`) marks that operation `ownersWish`: the step's receipt is then marked `wish`, read in the same tick as its
`since`, and the clean-up leaves it: "Left running: … was asked for by the owner while being started." What
self-healing or Spark Console's own power cycle brings back on a run's behalf stays the run's: before the bring-back
(`bringBack`, `bringBackParked`) each run's receipt for it that still holds is noted (`receiptsHeld`, over `runsRan`),
and once it is back the receipt follows it, its new Docker id and `since`, in `saved-runs.json` too
(`receiptsBroughtBack`), so a pair in new containers, or one a power-on brought back, is still stopped; one the owner
asked for while it came back is marked `wish`. An item whose Spark couldn't be asked when its step ended keeps no
receipt and is stopped by its name, as before.

## Why

Stale placement stops the wrong thing; so does a name kept for hours.

## Today

Marked in the Rule text above. Only an ask that reaches the action is the owner's wish: when Sparkie answers from what
it sees (that the model already runs) without calling `start_model`, `restart_model` or `keep_running`, nothing is
noted, and a saved workflow's clean-up still stops what its run started.
