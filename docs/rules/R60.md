# R60

## Rule

**R60.** The lock-out net: confirm, or it goes back. A change that could lock the owner out runs only with a put-back
armed first, in the Spark's own systemd, which fires with the console, the network or Tailscale down.

- **Armed in the same call, before anything changes.** The root helper's `run --net` (R42; never with `--open`, whose
  groups could reach the timer) refuses while another guard is open on that Spark (`pending`, neither kept nor put
  back, not the proof's own), then, as root, copies the ways in to `/var/lib/spark-console/guard/<id>/`, writes
  `restore.sh` and `guard.py` beside them (the helper's own text: its sudo line lets nothing else be root), its lock,
  `pending` and the unit `sw-guard-boot-<id>` that runs the same put-back if the Spark restarts inside the window
  (held to 300 s), and arms the timer `sw-guard-<id>` for the command's own time limit plus 600 s. A change inside the
  net is held to 30 minutes. If arming fails or the call is hung up meanwhile, what this call made is taken away and
  nothing runs; a refusal never touches a guard this call did not make. Copies older than 7 days go when a guard is
  armed, never an open guard's.
- **The ways in** (design A 2.8, row 2, and the reviews of A13a): `/etc/ssh`, `/etc/default/ssh`, `/etc/hosts.allow`,
  `hosts.deny`, `/etc/nologin`, `/etc/sudoers`, `sudoers.d`, `/etc/sudo.conf`, `passwd`, `group`, `shadow`,
  `gshadow`, `nsswitch.conf`, `/etc/pam.d`, `/etc/security`, the system's and the owner's shell start files, the
  owner's `authorized_keys`, `authorized_keys2` and ssh `config`, `/etc/netplan`, `/etc/systemd/network`,
  NetworkManager's connections, `/etc/hosts`, `/etc/ufw`, `/etc/default/ufw`, `/etc/iptables`, `/etc/nftables.conf`,
  Tailscale's state file and `/etc/default/tailscaled`, systemd's files for ssh and tailscaled by name, the owner's
  linger file and service manager's units, and on Spark 2 the console's sign-in files but `sessions.json` (losing
  sessions is a sign-in, not a lock-out). A file is copied with its bytes, mode and owner; a link as a link, never
  followed; a folder with all in it; a path that is not there as not there. Each folder above them, up to the owner's
  home (and `/var/lib/tailscale`, `/var/lib/systemd/linger`), is kept as a folder: its mode and owner. Kept as text,
  to compare: Tailscale's settings and routes, the live firewall rules, and the running state: whether ssh,
  `ssh.socket`, sshd, tailscaled, NetworkManager, networkd and ufw ran and were enabled, ufw on or off, and the key
  Tailscale was signed in with.
- **After the command** it says what differs: what goes back by itself, and when; apart, what does not (the live
  firewall rules; Tailscale's settings when its state file is as it was); and, by name, what cannot be put back at all
  (a Tailscale sign-out or a sign-in as another key, a unit whose package went). It disarms only on the console's word
  (`keep`, after the console's check from outside), never by itself. If its timer was stopped while the command ran,
  what differs goes back at once, and it says so.
- **The put-back** (`restore.sh`: from the timer, after a restart, or `putback`) stops the command's unit (after a
  restart, without waiting) and puts back only what differs: exact bytes, mode and owner, through folders opened one by
  one without following a link; a folder above that is gone is made again, but only `~/.ssh`, the console's state
  folder, `/var/lib/tailscale` and `/var/lib/systemd/linger` are swapped back for a folder when a link stands there; at
  the home or a folder between a link is left, and what is under it is named not put back. What the change added in a
  copied folder is taken away, and a folder above the copy did not see only once it is empty. Tailscale and the console
  are stopped first and started after; it tells systemd, restarts `ssh.socket` when it ran (a moved port) and reloads
  what it put back (`stopped` and `put` name both, so a later try starts and reloads them too). Then each way-in unit
  whose file state moved goes back to enabled, disabled or masked, and one settled at the copy and now (running, or
  stopped or failed) the other way is started or stopped; one still starting or stopping now is waited for, then counts
  by where it is headed; one starting or stopping at the copy is left as it runs and named. After a restart a unit's
  file is put right and one that ran at the copy, whose file went back, is queued to start; none is stopped then. ufw
  goes on or off, but not while one of its own files could not be put back. An error on one path ends that path only.
  `result`'s first line counts what went back (a unit only when systemd said ok to each call) and what did not. A
  put-back that fails is tried three times, 20 s apart, each failure written down in `failures`. Once kept or put back
  it only clears what is left (`pending`, the restart unit).
- **`keep`** counts only while the timer still waits and once its stop succeeded; after a put-back it answers "already
  put back at …" with the result's count. **`putback`** puts back now, also with the timer gone; after a keep it puts
  nothing back. `check` names an open guard, when it goes back and whether its timer waits, and one left with no timer
  ("net left"). A walled command cannot stop or change the timer, write the guard's folder, take `pending` away, or
  make `keep` or `putback` count: the proof tries each (attempts 15 to 18, R42) on two guards of its own, which carry
  its mark, block no other guard, and are taken away by the next proof if one was left behind.

## Why

A change to SSH, the firewall, Tailscale or a sign-in can cut off every way the owner reaches a Spark, and the console
with it. Like `netplan try` and a router's "commit confirmed", the change goes back by itself unless it is confirmed,
from a timer nothing a change can reach (the one page, sections 4 and 7, item 2;
`docs/design-2026-11-13/a-workspace.md`, 2.8 and 2.13).
