# R32

## Rule

**R32.** Telegram (2026-11-11): the console polls Telegram from Spark 2 and never opens a route for it; only one loop
polls, started after the local port is bound, and a 409 backs off. A secrets file that can’t be read never ends the
loop: it sets `secrets-unreadable` and reads the file again every 60 s (a stop cuts that wait short),
so Telegram comes back by itself once readable; the loop ends only on shutdown, a disconnect, no token, no
pairing or a refused token. An update counts only from the paired private chat and user id; everyone else gets silence
(no reply, chat, brain call or write per update). The words go through `sparkieTurn` with `ctx.channel`, so R25 holds;
a press or typed yes from Telegram runs as via `telegram`, never `page`, and sets `ownerConfirmed` only for an owner-only ask
pressed there within the approvals below. Any guard
that treats a session as “not on the tailnet” treats a channel the same. A carry-on turn keeps both: the task’s
`channel`, and `away` for a signed-in device (R31). Actions in `PAGE_ONLY` (`undo_update`, memory, saved workflows,
keeping an eval or trial result, `propose_update`; not `install_update`: R54) never run from
a channel (memory the owner says there does, R25): they become an owner-only button, pressed on the page with the passkey. No action may change access, keys,
passkeys or devices. `tell()` is the only sender and sends only a reply, the result or carry-on of work started in
that chat, an ask that waits for the owner's yes (below), or a fixed line (pairing, `/status`, “restarted while answering”, and the idle power-off’s one note the
first time it can act, R41): plain text, previews off, masked (but R68's whole lines); results by code with no log,
address or secret (an install's says why); the pairing code only in the answer to the passkey-confirmed `PUT` or `POST` that made it, never a
plain read; at most 20 sends a minute and 6 results an hour; a result that fails for now is tried 4 times, the wait doubling from a
minute, a 4xx once, one dropped journalled (A-8); 20 owner messages a minute in, one turn at a time. One
line goes out unasked, only after the owner switched it on with the passkey (`PUT /telegram/needs`: on needs the
passkey and a paired chat, off never does; the switch is kept with the binding in the secrets file, so disconnecting
or a new token turns it off and no restore turns it on): when something new joins the open-problems list
(`openProblems`, by its entries' keys) and has stayed on it 5 minutes (`SPARK_CONSOLE_NEEDS_SETTLE_MS`; one that goes
and comes back starts over), so what puts itself right sends nothing, `needsMeTick` sends “Spark Console: N things
need you. Send /status to see them.”, a count and nothing from the list, at most 3 in 24 hours, never while Telegram
isn't working, with no brain turn and no action. A problem told counts as new again only after 6 hours off the
list. What was told and when is in `telegram.json`, so a restart repeats nothing. It is not an action: no tool, agent,
`/mcp`, `POST /actions` or Telegram message can switch it. The owner’s words (R34) are answered before the one-turn
check, so they work while a turn runs; `/pause` and `/restart sparkie` are on the audit with via `telegram`; a turn
ended by `/stop` sends nothing more. The bot token and the chat binding live only in
`~/.config/spark-console/secrets.json` (0600), outside the state folder, are typed only on the passkey page, and
appear in no result, log, event or audit line. `SPARK_CONSOLE_TELEGRAM_API`, `SPARK_CONSOLE_SECRETS_FILE` and
`SPARK_CONSOLE_TELEGRAM_LIMITS` need `SPARK_CONSOLE_ALL_LOCAL=1`. Telegram can always be removed without the passkey
and is never needed to sign in. The outside heartbeat (2026-11-14), the second sender, sends nothing: once the
owner saves a check's address, pasted in their own chat (R51) or with the passkey (`PUT /heartbeat`; both through
`beatSave`; only `https://hc-ping.com/<uuid>`; `DELETE /heartbeat` never needs it), `beatOnce` sends that host one GET every 5 minutes with no body, query or cookie and one
fixed User-Agent, follows no redirect and waits 10 s at most. Its tick starts in the listen
callback too, so a second copy never beats, and its first beat waits a minute (a save beats at once), so a console
that dies a few seconds after each restart never keeps the check green. The address is kept only in the secrets file
and is in no answer, log, event or audit line; typed in a chat, it is taken out before anything reads the words
(R51), and `maskSecrets` hides it anywhere (by its id, so a plain "hc-ping.com" stays). Beats failing for an hour are one
line on the open-problems list.
Its switches SPARK_CONSOLE_BEAT_ API, MS, LATE_MS and FIRST_MS need `SPARK_CONSOLE_ALL_LOCAL=1`.

Approvals from Telegram (A10a; owner decisions 20, 22): an owner-only question (`question` with `ownerOnly`) asked
in the owner's own page or Telegram chat, or a task of theirs, is also sent to the paired chat by `tgAsk` as one ask
built by code (the question and each yes whole, with the page's own buttons) while “Approve from Telegram” is on:
`approve` beside the pairing in the secrets file, on with the passkey (`PUT /telegram/approve`) or by a new pairing,
off without one, read as off for a pairing made before it existed, and off at once by `/lock` in the paired chat, read
before the minute's limit and the five-minute rule (only the page turns it on); `sparkie_setup` and `/status` there
say whether it is on. A press there runs it once as the owner's yes (`tgApproving`, then `runChoice` checks
`tgAskOpen`) only on an ask this console sent to the chat paired now, still open, whose action is not in `PAGE_ONLY`,
while fewer than 3 approvals from Telegram fell in the last hour and 10 in the last 24 hours (their times in
`telegram.json`, so a restart keeps them); otherwise it runs nothing and says it waits in Spark Console, whose page
still answers it. A typed yes never answers an owner-only button. Each approval is a line in the chat that asked and
a notice on the page. `/lock` and the switch off void an ask's Telegram side; a new pairing or a restart voids the whole
ask. An ask over 3,500 characters is not sent.

## Why

A stolen Telegram session or SIM swap must not become the owner on the page, undo a fix, erase memory or lock the
owner out; nothing leaves the house that the owner did not ask for.

## Today

Approvals from Telegram (A10a):
- An ask in an agent's conversation (`ask_sparkie`) is not sent to Telegram; the owner answers it on the page. The
  dangerous ask (A10b) sends it.
- While approvals from Telegram are off, an ask raised in the page chat sends nothing there, not even a notice.

The pull install’s GitHub token (C4a):
- The secrets file has two whole-file writers, the service and `pull.sh setup`, and no lock between them.
- `pull.sh setup` reads the token from a pipe with no terminal, so a careless `echo` leaves it in history.
- `pull.sh setup` can’t tell a read-only token from a wider one, and doesn’t say to delete the old one on GitHub.
