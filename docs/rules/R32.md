# R32

## Rule

**R32.** Telegram (2026-11-11): the console polls Telegram from the hub and never opens a route for it; only one loop
polls, started after the local port is bound, and a 409 backs off. A secrets file that can’t be read never ends the
loop: it sets `secrets-unreadable` and reads the file again every 60 s (a stop cuts that wait short),
so Telegram comes back once readable; the loop ends only on shutdown, a disconnect, no token, no
pairing or a refused token. An update counts only from the paired private chat and user id; everyone else gets silence
(no reply, chat, brain call or write per update). The words go through `sparkieTurn` with `ctx.channel`, so R25 holds;
a press or typed yes from Telegram runs as via `telegram`, never `page`, and sets `ownerConfirmed` only for an owner-only ask
pressed there within the approvals below. The paired chat has the same owner controls as the page (owner decision,
2026-11-17). Server-only proof of the authenticated update, captured before a wait and bound to that pairing,
is copied through the request and checked when it acts. Channel and sender strings alone grant no authority.
A carry-on turn keeps its pairing mark; a signed-in device keeps its session marker. An agent never inherits the
owner's proof. Administration uses shared validated operations, with the same exact owner confirmation in either
interface; it never impersonates a page or tailnet request. Passkey enrollment needs a real authenticator ceremony.
`tell()` is the only sender and sends only a reply, the result or carry-on of work started in
that chat, an ask that waits for the owner's yes (below), or a fixed line (pairing, `/status`, “restarted while answering”, and the idle power-off’s one note the
first time it can act, R41): plain text, previews off, masked (but R68's whole lines); complete masked results and errors, with their useful details; the pairing code only in the answer to the passkey-confirmed `PUT` or `POST` that made it; ordered sends with Telegram transport backoff; one that fails for now (no answer, a 409
or 429) is tried 4 times on its own wait, doubling from a minute, only to the pairing it was for; any other 4xx once; one dropped journalled (A-8); 20 brain requests a minute in, one turn at a time; deterministic owner controls and approval callbacks are not dropped by this brain limit. One
line goes out unasked, only after the owner switched it on with the passkey (`PUT /telegram/needs`: on needs the
passkey and a paired chat, off never does; the switch is kept with the binding in the secrets file, so disconnecting
or a new token turns it off and no restore turns it on): when something new joins the open-problems list
(`openProblems`, by its entries' keys) and has stayed on it 5 minutes (`SPARK_CONSOLE_NEEDS_SETTLE_MS`; one that goes
and comes back starts over), `needsMeTick` sends “Spark Console: N things
need you. Send /status to see them.”, a count and nothing from the list, at most 3 in 24 hours, never while Telegram
isn't working, with no brain turn. A problem told counts as new again only after 6 hours off the
list. What was told and when is in `telegram.json`: a restart repeats nothing. It is not an action: no tool, agent,
`/mcp`, `POST /actions` or Telegram message can switch it. The owner’s words (R34) are answered before the one-turn
check, so they work while a turn runs; `/pause` and `/restart sparkie` are on the audit with via `telegram`; a turn
ended by `/stop` sends nothing more. The bot token and the chat binding live only in
`~/.config/spark-console/secrets.json` (0600), outside the state folder, are typed only on the passkey page, and
appear in no result, log, event or audit line. `SPARK_CONSOLE_TELEGRAM_API`, `SPARK_CONSOLE_SECRETS_FILE` and
`SPARK_CONSOLE_TELEGRAM_LIMITS` need `SPARK_CONSOLE_ALL_LOCAL=1`. Telegram can always be removed without the passkey
and is never needed to sign in. The outside heartbeat sends no content: once the
owner saves a check's address, pasted in their own chat (R51) or with the passkey (`PUT /heartbeat`; both through
`beatSave`; only `https://hc-ping.com/<uuid>`; `DELETE /heartbeat` never needs it), `beatOnce` sends that host one GET every 5 minutes with no body, query or cookie and one
fixed User-Agent, follows no redirect and waits 10 s at most. Its tick starts in the listen
callback too, so a second copy never beats, and its first beat waits a minute (a save beats at once), so a console
that dies a few seconds after each restart never keeps the check green. The address is kept only in the secrets file
and is in no answer, log, event or audit line; typed in a chat, it is taken out before anything reads the words
(R51), and `maskSecrets` hides it anywhere (by its id, so a plain "hc-ping.com" stays). Beats failing for an hour are one
line on the open-problems list.
SPARK_CONSOLE_BEAT_ API, MS, LATE_MS and FIRST_MS need `SPARK_CONSOLE_ALL_LOCAL=1`.

While approvals are on, `tgAsk` sends the paired owner code-built questions with all facts and exact commands,
split in order;
the approval becomes usable only after every part is acknowledged. A failed part stops delivery before any active
button. `tgApproving` and `runChoice` check `tgAskOpen` against the exact sent ask and current pairing.
Both interfaces use each choice once. A typed yes never answers an owner-only
button. There are no Telegram-only hourly/daily approval caps or hidden action lists. Each approval appears on
the page with its true origin, never as a passkey check. `/lock` and the switch off invalidate outstanding
Telegram approvals. A fresh strong owner confirmation can enable approvals again without reviving any old ask.
A restart, new pairing, expiry or changed payload invalidates the ask. Full questions and labels bind plain buttons too (A50; channel card).

Policy and test changes: `docs/telegram-owner-parity.md`.

## Why

The owner uses Telegram as the main control interface. Both interfaces need the same capabilities and exact
confirmations; strangers, agents, stale requests and incomplete delivery must never acquire owner authority.

## Today

Former approval policy, superseded by owner parity; retained as the record:

Approvals from Telegram (A10a):
- An ask in an agent's conversation (`ask_sparkie`) is not sent to Telegram; the owner answers it on the page. The
  dangerous ask (A10b) sends it.
- While approvals from Telegram are off, an ask raised in the page chat sends nothing there, not even a notice.

The pull install’s GitHub token:
- The secrets file has two whole-file writers, the service and `pull.sh setup`, and no lock between them.
- `pull.sh setup` reads the token from a pipe with no terminal, so a careless `echo` leaves it in history.
- `pull.sh setup` can’t tell a read-only token from a wider one, and doesn’t say to delete the old one on GitHub.
