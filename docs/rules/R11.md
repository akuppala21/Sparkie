# R11

## Rule

**R11.** New actions run only through `runAction`, in its order; a `read` action changes nothing; anything new that
changes a Spark goes through `runAction`, a claim, a job and `run`. Today: `GET /workflows` calls an action’s `run`
directly; `maybeHeal` calls `restartChecked` directly; page Deploy, Stop, brain start, stop and switch, downloads
and file writes skip `runAction`; `watchBrain` and `bringBack` run docker with no job; the owner’s
`/restart sparkie` word (R34) is a second caller of the same `restartBrain()` (one at a time), also with no job; when
the brain’s container is gone the word starts the page’s `main-start` job (claimed, no `runAction`), and so does the
brain keeper (R19). Neither may be copied for anything that starts or deletes. `save_file` goes through `runAction`
and the worker with no claim or job (R37); that is not to be copied for anything that starts, stops, replaces or
deletes. `keep_running` adopting an app that already runs changes only the list, so it has no job, and so does its
stop while the app’s Spark is off (`forgetApp`); its starts, restarts and stops are jobs with claims (R38). `files` (a
read) checks the shared folder is there before the worker looks, since the worker would make it (R37). `self_test` runs
through `runAction` and starts one `self-test` job, which holds no claim itself; each of its steps is an action run
through `runAction` (`start_model`, `stop_model`, `keep_running`) with its own claim and job, as Spark Console (via
`page`, actor `Self-test`, a fixed owner viewer, `healOwner()`), the same way “Test the changes” runs its steps
(`stepRun`, shared by both). Two direct `run` calls are in it: the healing drill’s `docker kill --signal KILL <id>`
(under a claim on that Spark, released at once; the id is the 64-hex id of the container the test itself started), and
fixed reads (`docker inspect`, `docker logs --tail 20` of the job, parsed for numbers only). Neither may be copied for
anything that starts or deletes. It touches only what it started: its model by the full id of the container its own
start made (a name says nothing about whose a container is), its web page and job by their own names. Its model’s stop
asks as the page when nothing of anyone else’s is under way on that Spark, and as a workflow step (via `workflow`, actor
`Self-test`) when something is, so `stop_model` cancels only the self-test’s own steps (an owner’s download-then-start
there is never cancelled); `stop_model` itself is unchanged. Its stops always carry `stop_model`’s validation pass when
that waits for its first run, the clean-up’s too. After a restart of Spark Console cut a self-test off,
`selfTestRecover` (5 s after start-up, `SPARK_CONSOLE_SELFTEST_RECOVER_MS`) stops what `self-test.json` says it started,
through `runAction` (`stop_model` for the model, only while its container’s id is the one recorded; `keep_running` stop
for its web page and job, kept first when cut off before joining the list), then one notice, also in the chat that
asked. The watcher’s cut-off notice (“check it’s running; if not, start it again”) is not given for the self-test’s own
operations (`selfTestCutOff`).
