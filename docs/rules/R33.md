# R33

## Rule

**R33.** Ways in that need no other device (the owner, 2026-11-11): three, any one enough. Tailscale on the device;
the owner’s passkey; one of 10 recovery codes. Recovery codes are made only with the passkey (`POST /auth/recovery`,
and never from an internet session while no passkey exists), are shown once, are kept only as hashes in the secrets
file (never the state folder, so no backup or rollback revives a used one), work once each, and are limited per
address only (10 tries in 10 minutes). Each use is on the audit and a notice says how many are left. `GET /whoami`
tells a visitor who is not signed in whether a recovery code would sign them in now (`recovery`: true when at least
one unused code can be read; yes or no, never how many), with or without a passkey on file, and the sign-in page
offers the code from it (F18). A browser signed in with a recovery code, or let in with a code the owner approved with
the passkey or paired Telegram confirmation, may add its own passkey once within `NEW_DEVICE_PASSKEY_MS` (15 minutes) without another passkey to
confirm it (`newDevicePasskeyOpen` in `passkeyGate`) while a passkey is on file; with none, the first passkey is set
up on the tailnet only; every passkey added from an internet session is a notice. Nothing else is loosened: every
other gated change still needs a passkey. Sparkie can say what the ways in look like and never change them (A5):
`sparkie_setup` carries `access` (devices signed in without Tailscale, passkeys by name, recovery codes left; names,
times and counts, never an address, hash or id; names labelled as data) only on the owner’s own call: `POST /actions`,
or Sparkie in the owner’s own chat on the page or Telegram. An agent’s key, `ask_sparkie`, a chat an agent started and
a saved-workflow step never get it. A file that can’t be read is a `problem` line, never “none” or “0 left”.
While state put back waits for the owner to look at what came back (R23), from the internet a passkey, a recovery
code, a device code and an agent key get one plain line, and `whoami` offers neither (`signin` and `recovery` false);
agents' changes are refused on the tailnet too. Verified owner requests and ordinary workload confirmations work
on the page and Telegram; they never lift the hold. Sign-ins and access grants remain held. Exact owner review,
re-enabling approvals and browser denial remain available. The tailnet door, `go-back.sh` and update rollback work.

The already paired owner can use `/device CODE allow|deny` for a waiting webpage sign-in. The complete strong ask
binds its private request identity, name, source and expiry. Approval is one-use; redemption rechecks the same
pairing, owner and request. `/lock`, re-pairing and a restored-access hold prevent it. Denial grants no access and
remains possible during the hold. This command does not admit terminals. HTTP approvals retain their passkey gate.
`whoami.deviceSignin` reveals only whether this route is available; the page offers it even with no passkey on file.

## Why

Being on only a phone or only a laptop, or on a browser that bypasses Tailscale, must never lock the owner out; a used
recovery code must never work again.
