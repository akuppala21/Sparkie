# R29

## Rule

**R29.** A step lands on `main` on its affected tests and the short check; the whole suite of `main`'s new tip
follows every landing, and an install still needs the whole suite passed on that exact build. `node tools/land.mjs
<branch>` lands a step. It refuses a branch that doesn't hold `main`'s tip (`--catch-up` merges `main` in, makes the
generated files again instead of merging them, and stops only on a conflict in a file written by hand), a work folder
with changes not committed, and a failing `node tools/make.mjs --check` on the branch with `main` in it. It asks a
compute Spark for what `pick --landing` gives: the test files that ran each changed function, every changed test file
and the short check; the whole suite when there is no map for `main` or a commit before it, a part was added or
removed, a changed line is outside any function, more than eight parts changed, or a path every test depends on
changed (`test/lib.mjs`, `test/start-mock.mjs`, `test/mock/`, `test/lock.mjs`, `tools/`, `deploy/`, `worker.py`,
`passkey.mjs`, `dig.mjs`, and the parts `03-identity`, `03-secrets`, `22-passkey`, `22-sessions`,
`25-backup-and-start`); `service/config.json` adds only the short check, and so do lines that are only comments and
a whole new function at the top level (its changed callers bring their own tests). `--whole` asks for the whole suite
whatever the pick. The plain `pick`, for GitHub's quick job and Sparkie's own changes, keeps design C 2.4's stricter
list: also a function most test files run, the core parts, `config.json`, and any changed line outside a function. Documents alone pick the documents test alone. It
fast-forwards `main` only if `main` hasn't moved meanwhile, one landing at a time, a line in `spark-landings.log`
each. After a landing that changed code (and wasn't just tested whole) it queues one whole run of `main`
(`SPARK_LAND_TIP_OUT` names the queue) and doesn't wait: a pass leaves the lock and map that are that build's tested
record, the base the next pick measures from; a failure names the landings since the last tested build, and a failed
file the pick would not have run is kept in that build's map (`missed`), so the next pick adds it. Before installing, `node test/lock.mjs` passes on the exact tree
(here, on a compute Spark or in GitHub's `suite` job), and the installer's lock check is unchanged. Every action is
in `TOOLS` or `CHANGE_TOOLS`. The lock names the build (`build`, `versions`) and what was tested: `tree` (git’s hash
of the files tested, the lock itself left out), `commit` (only when those files are exactly HEAD’s), `run` (the
GitHub run, only on GitHub) and `brainReads` (sha256 of the system prompt and every tool’s name, description and
inputs, as the stand-in brain was sent them). A copy without `.git` leaves out `tree` and `commit`. With
`SPARK_TEST_MAP=1` a passing whole run also writes `test/affected-map.json`: for every function of the parts, the test
files that ran it (Node's own coverage, one folder per test file), named by the same tree, or on a Spark by the
runner's `SPARK_TEST_TREE`; the runner's watcher asks for it on every whole run and brings it back beside the lock.
Git keeps neither file: on GitHub, after a passing full run on a push to `main`, the `mark` job (contents: write,
runs no repository code) checks the lock names that commit, tree, run and build (sha256 of `server.mjs`, `dig.mjs`
and `passkey.mjs`, computed in shell) and pushes the tested commit plus the lock as the tag `tested/<first 12 hex of
the tree>`, never a branch. The job that runs repository code (`suite`) has contents: read and keeps no credentials.
On Spark 2, `deploy/pull.sh install <tree>` installs only the newest commit on `main` (first parents) whose tree has a
`tested/` tag, and only when the tag adds nothing but the lock to that commit, the lock names that tree and the build
the code is, and the tree holds plain files only (no link, no submodule, no `.gitattributes` with `export-`); it is
the installed build’s copy that judges. Its read token is the secrets file’s `github` entry, typed once in a terminal
(`pull.sh setup`), handed to git only in its environment.
Today: from the Mac the installer still compares only the lock’s build id, so a `worker.py`-only edit installs with
every workflow untested (off) and crash restarts off; `pull.sh` compares the tree. The incoming tree’s own installer
still writes the way back and judges the install (C4b moves both to the installed build). Today: a watcher
started before this rule doesn't ask for the map, so until it is restarted every pick of a code change is the whole
suite; GitHub's run records no map; coverage misses a service killed before it wrote its record (that pick is too
small, and the whole run after catches it).

## Why

An unlocked build has every workflow off. A whole suite for every small step made steps slow and then batched; the
whole run after each landing, and before each install, still catches what a pick misses.
