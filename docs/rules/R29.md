# R29

## Rule

**R29.** `node test/lock.mjs` passes on the exact tree before installing; every action is in `TOOLS` or `CHANGE_TOOLS`.
The lock names the build (`build`, `versions`) and what was tested: `tree` (git’s hash of the files tested, the lock
itself left out), `commit` (only when those files are exactly HEAD’s), `run` (the GitHub run, only on GitHub) and
`brainReads` (sha256 of the system prompt and every tool’s name, description and inputs, as the stand-in brain was sent
them). A copy without `.git` leaves out `tree` and `commit`. Git doesn’t keep the lock: on GitHub, after a passing full
run on a push to `main`, the `mark` job (contents: write, runs no repository code) checks the lock names that commit,
tree, run and build (sha256 of `server.mjs`, `dig.mjs` and `passkey.mjs`, computed in shell) and pushes the tested
commit plus the lock as the tag `tested/<first 12 hex of the tree>`, never a branch. The job that runs repository code
(`suite`) has contents: read and keeps no credentials. Today: the installer still compares only the lock’s build id, so
a `worker.py`-only edit installs with every workflow untested (off) and crash restarts off; the lock’s `tree` closes
that once an installer compares it.

## Why

An unlocked build has every workflow off.

## Today

Marked in the Rule text above. Since R46 the Rule text says less than holds: every action is also in one group, and
`brainReads` also covers what other rounds can send (every action’s text, inputs and group, the cap, the groups’ words,
the lines that follow tools, the brain setup’s sampling and limits), not only what one turn was sent.
