# R23

## Rule

**R23.** Event types and `knowledge.workloads` fields keep their meaning; events stay rare. `spark-offline` carries
`last` (the last readings, only if under 3 minutes old) and, for a Spark Spark Console powered off itself,
`poweredOff` (why), and `spark-online` carries `upSeconds`. `spark-powered-off` (`why`: idle or asked, `by`, `parked`:
container names) is written once the plug is cut, and `spark-powered-on` (`why`) once the Spark answers again and its
record goes; both are on purpose, never a fault (`describeEvent`, `darkPeriods`). Docker not answering on a Spark that
is on is one `notice` (carrying `spark`) per outage, held by `knowledge.sparks[id].dockerDownAt` until Docker answers
again; it never writes `removed`. A row on a Spark that is off or not answering is never changed for that; only the
`workloads` action and fleet notes show it as last seen, not running (`sparkOff`, `19-watcher.mjs`). The copy of the
state posts one `notice` when no copy is newer than 7 days and the state changed since, and none again until a copy
lands (`noticedOn` in `backup.json`); never before day 7. The copy goes only to a Spark that is awake and never
turns one on; before Spark Console powers a Spark off, that Spark gets one first if the state changed since the newest
copy (`copyBeforeOff`), waiting no longer than a copy may take, and a copy that fails is recorded while the power-off
goes ahead. No copy holds `sessions.json`, and `restore.sh --with-state` never puts it back, so every device signs in
again; a sign-in alone sends no copy (nor does a passkey's or agent key's last use). Nor does a copy hold
`saved-runs.json`, and `restore.sh --with-state` removes it: a run's record from then would stop what runs now (R57).
The rebuild steps for a lost
Spark 2 disk (`deploy/REBUILD.txt`, shipped with the recovery files and named by `/help`) say where the newest copy
is, that it may be 7 days old, what comes back and what is given again.
State put back lets no device or key in by itself (contract 6.25, `22-putback.mjs`). The auth serial is kept in the
state (`auth-serial.json`) and in the secrets file, which no copy holds. A state that holds a passkey or an agent key
always has one (1 from the first); each removal by the owner (a device signed out, a passkey, an agent key, a right
taken from an agent key, agents paused) raises both, and the secrets file notes what went. `restore.sh --with-state`
removes the state's number. At start it is a put-back when something the secrets file notes as removed is in the state
again, whatever the numbers say; when the state's number is below the secrets file's (a state with no number is one
when the secrets file has a number); or when the state has a number and the secrets file none (a new disk). Then what
was removed since is removed again (a right taken from a key too), every device is signed out, the owner's pause comes
back, a task under way is parked with a line in its chat, and the hold follows until the owner, on the tailnet,
presses "Keep these" on the list of what came back (with the passkey, if one is set up). Under the hold, from the
internet, a passkey, a recovery code, a device code and an agent key get one plain line and `whoami` offers neither,
agents' changes are refused, and an approval from Telegram waits; the tailnet door, the owner's own chat and Telegram
requests, `go-back.sh` and an update's way back work as always. A secrets file that can't be read keeps the last
answer read while Spark Console runs, so a hold doesn't lift; after a start with the file unreadable, nothing is held
until it reads again. Each narrowing notes only the right it took, and a put-back takes again only those.
A job (`keep_running` with `once`, A13) that ends is one `notice` (carrying `spark` and `container`), once: its row
keeps `endTold` until it runs again, and the first look at a Spark that Docker answered only marks what had ended
(`knowledge.sparks[id].sawContainers`, set by that look even when it finds nothing, so the first job on a Spark first
seen empty is told). The line is built from its name, how it ended and when, never its log. `spark-offline` for a
Spark Spark Console powered off, and `spark-online` after a planned wake, carry `planned: true` (D4).
`run` with `minutes` (A6) is an operation of type `run`, after code has decided all it decides without them (the
sorter, the ask, the rail, the walls, the copies, the journal’s start and end lines). A look is held to 1 minute, a
change that runs at once to 10, an asked one to 120, and the answer says when it was held. Its end is posted in the
chat that asked through `postResult`, like every operation's (which wakes the carry-on), built by code: where, how
long, the exit code and its record, never its output. An exit code other than 0, or its limit, is a result; it fails
only when it could not run. `cancel_operation` stops its unit by id (`/stop` does not, R34); after a restart its unit
is stopped by id once its Spark answers, and the one cut-off notice says so. It never runs again. Not on Spark 2 yet.

## Why

Healing reads a 500-event window; the passkey gate reads `byConsole`; the intent gate picks a stop or restart target
from the watcher’s view.

## Today

- After a start with the secrets file unreadable, nothing is held until it reads again: a hold on record lifts
  meanwhile (only the owner's own account on Spark 2 or a damaged disk can make it unreadable; refusing the internet
  whenever it is would be the worse trade).
- A put-back takes from an agent key a right the owner took and later gave back: a giving is not noted. It fails
  closed; the owner gives it back again with the passkey.
