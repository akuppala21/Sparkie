# R55

## Rule

**R55.** What `run` does with a change (R42 is the root helper and the look). First the sorter: code, never the brain,
sorts every command before anything runs, from its text and where it runs alone (`sortCommand`; no model call, no file
read, bounded work, never a throw for anything JSON can carry): a look, a change, risky, the lock-out class or not done,
in that order of danger, and when two could apply the later wins (design A 2.8; the one page, section 4).

- **The careful answer is the default.** A command is a change only when the sorter can show it is one: a program it
  knows, called by a name or path it resolves to that program, each option and sub-command on that program's list (its
  manual's, `20-options.mjs`), every word that decides what it does in view, touching only places it can place. Anything
  else is risky: an unknown program, option or sub-command, a `$` where an option or its value (unquoted, so bash may
  split it, unless it is `$(nproc)`), a program or a path goes, a loop or other shell form it does not read, a sign that
  is not plain ASCII, words a program reads from its input (`xargs`, `find -exec`; a plain reader fed by `xargs` stays a
  change), code fetched from the network and then run, code run with a word naming a file this command (or, by
  `opts.written`, an earlier one of the task) wrote or holding an address, or run from or handed a folder it wrote into
  (an npm, yarn or pnpm install runs the project it stands in; a local package handed to an installer is code it runs),
  and a command run on another machine or a copy onto one (`ssh`, `scp`, `git push` to an address, tar's `host:file`; to
  a named remote it is a change: where that points is in settings the sorter does not read). A program run by another
  (`conda run`, `git rebase -x`) is sorted where it stands. A walled change runs git with its hooks and fsmonitor off
  through the environment (`GIT_CONFIG_COUNT`), so what could undo that is asked: setting or unsetting a `GIT_*` name
  (`env -u` and `env -i` too), `git -c` or `--config-env`, and `git config` writing, unsetting or removing a key that is
  not plain (`core.hooksPath`, `core.fsmonitor`). A sign that does not show is not done.
- **A look** keeps `run`'s own checks (`lookForm`'s exact forms, no `sudo` command word, no key word) and every program
  in it only reads, with no flag that writes, no redirection but to `/dev/null`, no here-document. It runs in the look
  wall, so a wrong "look" still cannot write or send. A key shown back is not done.
- **Places** (`20-places.mjs`): a change that names a way in anywhere, even to read it, is the lock-out class (SSH,
  users and sudo, PAM and shell start files, the network, the firewall, Tailscale, linger, their units, the console's
  unit and sign-in files); one that reaches the root helper or its sudo line is not done and is answered with the
  owner's one-time command; a disk or device, the kernel, a schedule, Docker's settings and the console's or the brain's
  files are risky; so is writing what something outside the wall later runs or reads (the PATH, user units, tool
  settings, git hooks and settings, Python at the top of the home). A path is placed against the owner's home (`home`,
  else the configured user's): another user's home, or a path climbing out of it, stays itself, and so does `/root` (its
  ways in listed too); a write under `/home` outside the owner's is risky. A folder above a way in counts for a command
  that reaches everything under it (`rm -r`, `chmod`, an archive, a patch or git's work tree written there; `tar -P` and
  `unzip -:` reach `/`), and every name a program works out counts too (a suffix put on or off, a counter, a backup
  suffix, curl's `#1`, a copy's own name). A `cd` narrows where the command stands only when it is first in its chain or
  right after `&&`, with no `!`, in a chain not sent off with `&`: for the rest of the chain while `&&` follows, for
  good after `|| exit`; otherwise every folder a cd reached counts. As root, a path word of a change outside the root
  folders (a home, `/etc` less the lists, `/opt`, `/srv`, `/mnt`, `/data`, `/tmp`, `/var/tmp`, `/var/www`, below
  `/usr/local` but its `bin` and `sbin`) is risky, and only a plain command (one program, nothing set before it) runs at
  once; a script, a one-liner or a flag that runs a program is asked, and so is `systemctl` but to start, stop, restart,
  reload, enable or disable a service named plainly, not one of systemd's own. No wall guards the Spark's own ports from
  root: a root download naming a host by number, localhost, a one-word or fleet name, or forcing an address is asked
  (root's other ways to a port already are).
- On Spark 2 every change is risky. `sudo` and `su` in a command are answered "set root".
- **The reason** is the sorter's own words; a piece of the command in it is one quoted line, cut short, with no control
  sign, so a command cannot write a line of what the owner is shown.
- **The result** carries what the next steps use: `kinds` (the dangerous asks: root, lockout, delete, brain), `form`,
  `simple` (may have an "always" kind), `open` (needs what the run wall hides), `deletes` (risky unless every named file
  is copied first), `scripts` (to hash for the ask), `answer` (`set root`, `owner command`), `lasting`, and `placed` and
  `wide` (the files it changes and the folders it reaches everything under: what the runner copies first; each word as
  written and as bash makes it, and a `*`, `?` or `[` in them is read by the runner as a pattern and as the exact name).

## Why

Sparkie may change a Spark at once only where the copy first, the walls and the owner's words stand behind it; the
mistake that matters is a command run at once that should have been asked, guarded or refused (design A 2.5, 2.8, 2.13;
the one page, sections 4 and 7; the reviews of 2026-11-14 and 15).

## Today

Dark: nothing calls `sortCommand` but its test, and `run` still sends every command to the look wall. Steps A7b (the
runner, the copies) and A7c (the ladder, the ask) wire it in. It sorts one command at a time and remembers nothing:
fetched by one command and run by the next is two plain changes (the runner carries this from A7c on, passing what a
task's changes wrote as `opts.written`). A link on disk a path goes through is not seen. git: hooks the settings point
at tracked files run with a pull (the runner carries this from A7c on: git runs with hooks and fsmonitor off), and a
work tree above the folder git stands in is not reached. An address with no `://` (`npm install evil/x`,
`git@e.com:x.git`) is not seen, and `pip install <name>` puts programs in `~/.local/bin` under names the package picks.
Interpreters' one-liners are read only for names, a script's text not at all, and what sed or awk text writes (`w file`)
is not placed. Left to the walls: names a program never expands or builds in a one-liner, a host only DNS or a redirect
makes the Spark (as root not seen), a plain reader's options (any but those that write or run). As root, by the one
page's choice, a file under `/etc` or `/usr/local/lib` that root or every Python later runs (`…/dist-packages/x.pth`) is
an at-once change, and `~` is the owner's home. `placed` and `wide` (at most 256 paths, none with a control sign) also
hold sources and words an option may name; not what code it runs writes (a build, an installer, a script), nor git's
work tree above the folder, nor a name picked at random (`mktemp`) or numbered to keep an old file (wget's `x.1`).
