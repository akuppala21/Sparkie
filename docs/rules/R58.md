# R58

## Rule

**R58.** Updates from chat (design C 2.3, step 5; contract 6.24): `check_update` (a lookup in the group `updates`, the
owner's and any read key's) runs `pull.sh check --json` on Spark 2, from the copy every install leaves beside
`go-back.sh`, as `/key GITHUB` runs `pull.sh setup` (R51). It says which build is installed; the newest commit on `main`
with a `tested/` tag, and whether it is newer (never one older than the installed commit, as `pull.sh install` refuses
it, R30). The installed commit is the installed lock's `commit` when Spark 2's copy holds it (and it holds the lock's
`tree`), else the newest commit on `main` whose tree is the lock's `tree` (a lock from a whole run on a Spark names
only the tree, R29); when neither is known (a lock from before that, files no commit on `main` holds) it says it can't
tell and offers nothing, and `pull.sh install` refuses, whatever the lock holds (only hex ids are read from it). Then:
whether it changes what the brain reads (the installed lock's `brainReads` against the tag's) and the eval on
record for it on today's case set (R47), or "not run"; that `main`'s newest commit isn't offered while it has no tested
mark; and at most 10 commit subjects since the installed commit. The subjects are outside text: labelled as data, and
`check_update` is not in `INSIDE_READS`, so a turn that read them counts as one that read outside text (R25). It
installs and changes nothing. The token never leaves `pull.sh`
(git gets it only in its environment, R29) and the answer is masked. When GitHub refuses the token (its own words:
authentication failed, invalid username, repository not found, 401, 403), the answer says to give a new one with
`/key GITHUB`, and the needs-you list (`openProblems`, the ways in) says so until a later check gets through; that is
kept in memory, so after a restart the next check finds it again. Not set up and unreachable are said, and put nothing
on the list. Without git on Spark 2 (it isn't on the fixed-path list, and no install refuses over it) the answer says
so and what to install, and the needs-you list says the same until a check finds git.
The newest tested tree is offered only when its tag passes `pull.sh install`'s own checks of the tag and its lock (that
commit plus the lock and nothing else; a lock naming that tree, and the build its three code files are, worked out
from git as `install` does); otherwise the answer says it
isn't offered and why (`badTag`: `pull.sh`'s own words, with the ids it checked). From the lock only a build id, a time
shaped as one and a 64-hex hash come out, never its text; git's own words, with the server's, come apart (`gitSaid`),
labelled as outside text. The fetch has 60 seconds (`setup`'s first, 300; `timeout`, which ends git's helpers with it);
`pull.sh` runs in a process group of its own, and at 120 seconds all of it ends, git with it. Either is said ("slow":
the fetch didn't finish). A lock git left in Spark 2's copy of the repository is named, with the `rm` that removes it
("locked"); nothing removes it by itself. A bad tag on `main`'s head is said once.

`install_update` (in `updates`, no input, never a saved workflow's step) installs the newest tested build from chat as a
dangerous ask (R54): no plain question before it; the ask names the tree with the build its code is (worked out as
`install` does), the day and time it was tested, the files that differ from the installed commit (names of a plain shape;
the rest counted), and whether it changes
what the brain reads or the eval's cases (the tag's lock's `evalSet` against today's), with the eval's result on the
cases its lock names or "not run" and, then, that Sparkie asks before every change until that result is kept. Nothing
is newer: said, nothing asked. The yes (the owner's, on the page or in the paired Telegram chat, with its two digits)
is refused while an install asked from chat is going (`update-asked.json` is there) or another yes is being checked;
it checks again that it is still the newest tested build (when that very tree was installed another way meanwhile, it
says so) and that no operation runs, keeps `update-asked.json` (the tree, the chat that asked, the channel), and
starts `pull.sh install <tree>` with `ASSUME_YES=1` outside the service (`systemd-run --user`, with
`RuntimeMaxSec=3600`), which restarts it. The press is answered within 40 seconds; what a longer check comes to is told
in the chat that asked. The result `pull.sh` writes is told once in the chat that asked, and on Telegram when it was
asked from there, by whichever build runs then (looked at every 10 s and after the restart); none in 90 minutes is said
too, and an asked time ahead of the clock counts as old (said so at once). At the unit's hour systemd stops `pull.sh`:
before the way back is armed its result says it was stopped before it changed anything (refused), and a stop while it
is being armed takes this install's way back again; after, the way back's own timer has put the build from before back
at 30 minutes. After a kept one the self-test is started once, as the owner's (it wakes nothing; a Spark that is off or
busy is said).
`pull.sh` keeps a new build only once each page's script is the new page's (`app.js` naming its build) and sign-in
answers as far as it can without a passkey: through the real address only where it can answer (through Funnel,
`/console/api/whoami` with `access`; over the tailnet the console refuses Spark 2's own address there), and on its
socket as a visitor from the internet (Funnel's header, no forwarded address), where `whoami`'s `signin` is what it was
before the install and, when a passkey can sign in, `/auth/signin/begin` gives a challenge.

## Why

The owner asks from the phone whether a newer tested build is out, and needs to know what it changes before saying yes.

## Today

- Whether the token has expired is known only by asking GitHub, so the needs-you line comes only after a check; so
  does the one for git.
- Where there is no `timeout` (a Mac), the fetch has no limit of its own, and the console's limit at 120 seconds can
  end git half way; the lock that leaves is then said, not cleared.
- The eval's line is not the rail's answer (R52): it is the newest result of any kind kept for the newer build's mark
  and the case set its lock names (today's when it names none). And while a passkey is set up, a passing full result
  for a build not yet installed isn't kept (only this build's can wait for the owner's yes), so before an install the
  line reads "not run" even after an honest run: run the eval again after the install, and keep its result with the
  passkey.
- Passkey sign-in itself, with a passkey, isn't tried before "kept": only that `whoami` says what it said before and a
  sign-in begins.
