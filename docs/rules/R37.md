# R37

## Rule

**R37.** Files (2026-11-11): Sparkie and agents reach files only in a Spark’s shared folder, only through the worker’s
`workspace-files` (`sharedFolder` → `sparkFiles`), never by building a path or command in Node; `worker.py` was not
changed. `files` lists 100 entries or reads one text file (the first 8,000 characters, its key shapes hidden by the
action itself (`hideKeys`), plain words never, labelled as data, not in `INSIDE_READS`). The worker makes a Spark’s
shared folder the first time anything looks there, so `files` first checks it is there (one fixed `[ -d ]`, nothing
from the request in it) and says when it isn’t yet: a read changes nothing. `save_file` writes one new text file of at
most 64 KB: it never replaces, renames, deletes or makes a folder, refuses text holding a key shape (a known token
format such as `hf_`, `sk-`, `ghp_`, `github_pat_`, `xox`, `AKIA`; a private key block, PGP’s too; a setting such as
`SECRET_KEY=` or WireGuard’s `PrivateKey =` with a long, random-looking value; a password inside an address), so plain
notes and code save; runs inside `runAction` (pause, audit) with no claim or job, and adds a `file-saved` audit line.
Its name has no invisible or direction-changing characters (`SAVE_PATH`), and its button shows the name whole. Both
refuse hidden names, `..`, absolute paths and links; `files` also refuses `*.pem`, `*.key`, `id_*`. More than two of
the owner’s file operations at once answer busy, saying to try again. From Sparkie a save runs at once only when the
owner’s words ask to save or write a file and name the Spark (this message’s; the message before only when this one
names none) and the whole path, as one word that ends like a file name; else a button. Never a saved-workflow step. A
job (`keep_running` with `once`, A13) is the one other writer: its folder `jobs/<name>` is the one path built in Node,
the fixed shared path and its checked name (`jobDir`, the path it mounts), made by one `mkdir -p` under `umask 077`
(`jobFolder`), never through the worker; then the job’s own container writes there at `/out` (as the user its image
runs as) and reads the whole shared folder at `/in`, read-only. The worker’s 64 MiB and 1,000-entry limit doesn’t
bound what a job writes, but jobs’ outputs count toward it: once they fill it, `save_file` is refused, saying the
shared folder is full, most likely with job outputs under `jobs/`, and how to clear them.

## Why

A file read is outside text; a write must never destroy the owner’s data or reach a file that runs.
