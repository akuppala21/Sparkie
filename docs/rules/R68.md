# R68

## Rule

**R68.** What `write_file` does (A7d): one text file on a compute Spark, the whole file or its lines `from` to `to`
(as `cat -n` numbered them; `to` = `from` - 1 puts the text before line `from`), through `run`'s ladder and runner
(R61), never around them.

- **Sorted by code from the path, never from words.** The sorter is handed a plain write of that path from where the
  change starts (`cat > <path>`; `~/…` and a whole path from the home, anything else from `~/work`), so the file is
  refused, asked or written at once exactly as a `run` writing it would be: Spark 2, a brain Spark, root, a pause, not
  done and the lock-out class refused; a protected folder, a place the plain wall keeps read-only, a link in its folders
  and the rest of `hostClear` as for `run`; `written` gets the path, so a later command of the request that runs it is
  asked.
- **The bytes** (at most 128 KB, no NUL, nothing a mask would hide: a key is given by its name) reach the unit on the
  helper's input (`run --stdin`), from the call's own script as base64, never on a command line. The unit runs code's
  own program: it writes beside the file and moves the new one into place, with the old file's mode (0644 for a new
  one), and only while the file is as code read it just before (its SHA-256, or not there); otherwise it writes
  nothing and says so.
- **The runner's own steps** (R61): the copies first (the old file, so undo puts it back), the journal's start line
  (`tool: write_file`, the path, the byte count; the bytes are not on a line), the run wall, the end line, the hold
  after an end it can't know, the memory cap and `--protect`.
- **Asked:** the button shows the path and the lines that change, old and new (masked, each line cut to 200, at most
  30 each way; a key file's old text and one over 256 KB are not shown), why it is asked and what put-back covers. Its
  call holds the same arguments; a press after the file changed since the ask is void and asked again.
- **Lines `from` to `to`** need the file there as plain text of at most 256 KB, with those lines in it; the text that
  goes in their place ends with a line break.

## Why

A file written by the brain is a change like any command (design A 2.9, 2.14 row 7, decision 18): the same gates,
the same copy first and the same wall, and its text never passes through a shell's words.

## Today

The design's "refused if the file changed since the last look numbered it" is the file as code read it just before the
ask or the run, not the brain's own look. `root` is not taken (it waits for the put-back net). Not in the box (`on:
"box"` is not built).
