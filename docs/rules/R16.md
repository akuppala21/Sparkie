# R16

## Rule

**R16.** Jobs record `ranHere` and `stoppedHere`, set `consoleStopped` before a purposeful stop, and return
`{outcome:'started', operation}`; failure puts back exactly that; a running copy of the same model that a start
replaces is renamed aside, never removed before the new one answers, on one Spark (`deploy`, F9) and across two
(`clusterDeploy`); `asideBack` starts it again on failure or cancel. Fixes retry 3 times at most.

Every stop of what an operation ran is looked at (A-23, `stopChecked`, `17-stop-checked.mjs`): `docker stop`, then
one `docker inspect` as `waitJobEnd` asks it, so Docker not answering is never "gone"; running, or no answer, is "not
stopped". On a Spark where something a start ran isn't known to be stopped, `putBack` starts nothing again there, and
`asideBack` leaves a copy set aside (it looks again after the put-back's own stops); both stay on the operation's
lists, and one sentence a Spark names both (`owedWords`, ending "… again" so the chat line carries it). It is the
operation's `cleanUp` (the cancel's answer and the chat line say it in place of "put back") and the failure's error
after its first line (`withOwed`). The same checked stop is in `appPutBack` (an app that didn't come up), in
`clusterParts`' `stopAll` (a stop that didn't take there is said, as an unreachable Spark is), and in `restartJob`:
once `docker start` worked, every bad end of the wait (a cancel, no answer to the test prompt, the limit) stops it
again and says which ("…, so it was stopped again" or "…, and it couldn't be stopped: it may still be running on Spark
3"); a container that ended by itself isn't stopped again. A `docker run` that timed out, or whose Spark stopped
answering, counts as run, so the put-back stops it. A one-Spark start's wait (`START_READY_MS`, 45 minutes) and a
restart's (`RESTART_WAIT_MS`, 30) are settable on the stand-in fleet (`SPARK_CONSOLE_READY_MS`,
`SPARK_CONSOLE_RESTART_WAIT_MS`); at the start's limit it says the start gave up on it. Out of memory, the context is
cut to 32,768 tokens, then 16,384 (`CONTEXT_FLOOR`), never shorter by itself (contract 6.9, T12, A-26); when that
doesn't fit the start fails and puts back what it stopped.

## Why

Put-back, the desired list, healing and chat read these. A put-back that starts something again beside a model that
may still be running can fill a Spark's memory (R2); "put back" said when it wasn't is a false sentence.

## Today

- A console restart in the middle of a start leaves the copy set aside stopped under its `-before-` name.
- What a put-back still owes is said, not done later by itself: T45 ("put back when it returns") isn't built.
- A context fixed in a setup the owner named (or the model's own `spark.json`) is still cut by the fix without asking:
  T42 needs a question inside a running operation, or a new argument, and isn't built.
- A run kept cut below 16,384 is lifted (`fullContext`, R48) only when it carries `contextCut` (kept since B3); one
  kept before that, at 8,192, can't be told from a setup that sets 8,192 itself, and is started as it was kept.
- A `docker run` the daemon finishes after the put-back's stop of it isn't stopped (the stop finds nothing yet).
- Across two Sparks, the errors "…, so both were stopped" (`clusterParts`) are written before `stopAll`'s result is
  read; when a part didn't stop, its own line and the put-back's words say so, and the first line still does.
- `appUp` (`21-apps.mjs`) takes Docker not answering for an app that stopped right after starting.
- Self-healing's bring-back of a pair (`20-heal.mjs`) stops and starts with the unchecked form; it starts again only
  what ran a moment before.
