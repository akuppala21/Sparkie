# R16

## Rule

**R16.** Jobs record `ranHere` and `stoppedHere`, set `consoleStopped` before a purposeful stop, and return
`{outcome:'started', operation}`; failure puts back exactly that; a running copy of the same model that a start
replaces is renamed aside, never removed before the new one answers, on one Spark (`deploy`, F9) and across two
(`clusterDeploy`); `asideBack` starts it again on failure or cancel. Fixes retry 3 times at most.

Every stop of what an operation ran is looked at (A-23, `stopChecked`, `17-stop-checked.mjs`): `docker stop`, then
one `docker inspect` as `waitJobEnd` asks it, so Docker not answering is never "gone"; running, or no answer, is "not
stopped". On a Spark where something a start ran isn't known to be stopped, `putBack` starts nothing again there, and
`asideBack` leaves a copy set aside: it first stops and looks at the new container of the copy's own name (W-1), and
looks again after the put-back's own stops; both stay on the operation's lists, and one sentence a Spark names both
(`owedWords`, ending "… again" so the chat line carries it; the new one of the copy's own name is called "the new …").
A pair stopped or set aside for the start (`<name>` and `<name>-part2`, `backUnits`) goes back whole or not at all
(W-7): both parts stay stopped when either Spark is held, a part that did start is stopped again when the other
didn't, and the words say to start the model across both Sparks again. What couldn't be started again (Docker's own
error, a job folder that is a link) stays on `stoppedHere` and is said too (W-3, `job.notBack`). All of it is the
operation's `cleanUp` (the cancel's answer and the chat line say it in place of "put back") and the failure's error
after its first line (`withOwed`). The same checked stop is in `appPutBack` (an app that didn't come up), in
`clusterParts`' `stopAll` (a stop that didn't take there is said, as an unreachable Spark is; its errors say "both
were stopped" only when both checked stops said so, else which part may still run, `stopsSaid`), and in `restartJob`:
once `docker start` worked, every bad end of the wait (a cancel, no answer to the test prompt, the limit) stops it
again and says which ("…, so it was stopped again" or "…, and it couldn't be stopped: it may still be running on Spark
3"); a container that ended by itself isn't stopped again. A `docker run` or `docker start` Docker didn't answer in
time, or whose Spark stopped answering (`unanswered`), counts as run (W-6): a one-Spark start's container and a part of
a start across two join `ranHere`, so the put-back stops them; a restart goes on to the checked stop ("Docker didn't
answer the start of … in time, so it was stopped again"); a new app is stopped again by `appPutBack`. A one-Spark start's wait (`START_READY_MS`, 45 minutes) and a
restart's (`RESTART_WAIT_MS`, 30), on the start and restart workflows' code lists (W-11), are settable on the stand-in fleet (`SPARK_CONSOLE_READY_MS`,
`SPARK_CONSOLE_RESTART_WAIT_MS`); at the start's limit it says the start gave up on it. Out of memory, an automatically chosen context is
cut to 32,768 tokens, then 16,384 (`CONTEXT_FLOOR`), never shorter by itself (contract 6.9, T12, A-26); when that
doesn't fit the start fails, puts back what it stopped, and says the way on: a setup that sets a shorter context itself
(a recipe setup, or the model's own `spark.json`) runs with it, since a setup's own context is never made longer
(W-14). A rejected context flag is never removed by the bad-flag fix: the start fails and puts back its changes.
Explicit context and selected/model-owned setup context are preserved (T42): put back, release claims, then ask the
owner before a separate shorter start. Waiting holds no claim; unresolved cleanup permits no retry. The private,
one-use proposal preserves the target, setup, stop permissions and original three-attempt/30-minute budget. A new
reduction needs a new press; expired, changed or restarted proposals fail closed. See `docs/context-retry.md`.
A run kept cut below 16,384 goes first with its full context, also when its record of the cut holds no free
memory figure (W-12).

## Why

Put-back, the desired list, healing and chat read these. A put-back that starts something again beside a model that
may still be running can fill a Spark's memory (R2); "put back" said when it wasn't is a false sentence.

## Today

- A console restart in the middle of a start leaves the copy set aside stopped under its `-before-` name.
- What a put-back still owes is said, not done later by itself: T45 ("put back when it returns") isn't built.
- A run kept cut below 16,384 is lifted (`fullContext`, R48) only when it carries `contextCut` (kept since B3, with a
  figure or none); one kept before that, at 8,192, can't be told from a setup that sets 8,192 itself, and is started as
  it was kept.
- A `docker run` the daemon finishes after the put-back's stop of it isn't stopped (the stop finds nothing yet).
- `appUp` (`21-apps.mjs`) takes Docker not answering for an app that stopped right after starting.
- Self-healing's bring-back of a pair (`20-heal.mjs`) stops and starts with the unchecked form; it starts again only
  what ran a moment before.
