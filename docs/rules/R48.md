# R48

## Rule

**R48.** Lessons (B2; contract 5.10): when an operation ends, code writes what failed into `lessons.json` in the state
folder, through its one writer, `recordLesson`, which `learnFrom` calls at `runJob`'s end, after the journal's record
of the operation. A lesson is a failure: its kind (`start`, or `app` for `keep_running` starting a container); its
subject (a start's model, engine and number of Sparks; an app's container and image); the setup tried (`how`:
`setup:<id>`, `proven` or `own`; `flags`, 12 hex of a hash of its flags and the names of its environment values; its
`image`; `on`, its Sparks in order; `code`, the start workflow's version); a known failure id (a `START_FAILURES` id or
`unknown`; for an app `image`, `docker` or `stopped-at-once`); `seen` or `proven` and the count `failed`; the journal
ids of its newest three operations (`evidence`); `firstAt` and `lastAt`. There is no `fix`: a start that worked after a
fix is replayed by its proven run (`verified.json`). Every value is one of the console's own, typed: a name its pattern
allows that `maskSecrets` leaves as it is, a hash, an id from a fixed list, a number or a time; anything else is stored
as null, so no lesson holds a log's words, the brain's or the owner's words, or a key. The same failure of the same
setup counts again while its image, Sparks and start code are unchanged; otherwise it is written anew with `failed: 1`.
Two or more of the same known failure make it `proven`; `unknown` stays `seen`. An operation that ended well leaves no
lesson, also when an attempt failed and a fix followed, and takes out the lessons of the same setup (a start: the same
model, engine and number of Sparks with the same flags, image and Sparks; an app: its container on that Spark). A
cancelled one gives and takes nothing. The start puts what it tries on the job before its first attempt (`setupTried`,
one line in `startWithFixes`, and on `START_CODE`), so the start workflows' versions changed once with this rule (R18).
At most 500 lessons, the newest kept.

A start reads them before it picks a setup (B3; design B 2.4). For each setup in `bestHow`'s order it works out the
lesson that setup would leave (`setupTried`, `lessonOf`) and passes it over when a `proven` lesson has the same subject,
`how` and `flags` and the image, Sparks and start code this start would use (`failedTwice`, `bestHowNow`); when one of
those differs, it is tried again. Only a failure of the setup's own counts (`PASS_OVER_FAILURES`): `out-of-memory`,
`bad-flag`, `garbage`, `no-answer`. One whose cause is outside the setup never does (`gated`, `port-busy`, `image`,
`memory-share`, `never-connected`: every setup meets that wall), nor one not on the list. The start's result
(`passedOver`) and its operation's log name each setup passed over, its failure, count, last date and lesson id.
When every setup there is failed twice (`passedOverAsk`): the owner's own
request (`POST /actions`, the page's own controls, or the yes below) runs the best of them and says so; Sparkie or an
agent gets a question whose yes runs it; self-healing and a call to the model address leave it, saying why. Lessons
that can't be read pass nothing over, so a lesson never makes impossible a start that would otherwise run. A run that
worked only once its context was cut to fit (out of memory) keeps the free memory then (`contextCut` in
`verified.json`); when its Sparks have more than that and 8 GB free now, its full context goes first (`fullContext`),
and running out of memory cuts it again. These joined `START_CODE`, so the start workflows' versions changed again.

The brain sees lessons as cards (B4): one line each, built by code from the typed fields, checked again as read
(`lessonCard`), shown as what happened and when, never as what to do. Up to six about the owner's words go in the record
block of the owner's own chats, never the system prompt, picked as memory lines are (`memoryCards`); the owner's picked
lines come first and the cards take what they leave of both rooms. A failed result names the lesson already on record
for that same known failure (`lessonSeenBefore`). `SPARK_CONSOLE_MEMORY_OFF` naming `names` turns the cards off.

## Why

A start that failed the same known way twice shouldn't be tried a third time blind (the one page, milestone 3), and
the record must be one that a log, a web page or the brain can't write into (contract 5.8).

## Today

- A job (`keep_running` with `once`) that ends with an error is told by the watcher after its operation has ended
  (`jobEnded`), so it is not an operation's end and leaves no lesson (the design's `job-exit`).
- How an app's start gave up is read from the opening words `21-apps.mjs` writes where it gives up (a name, then fixed
  words: `APP_FAILURES`), not from a field it sets. Any other failure of an app leaves none.
- A start from the page's Deploy with the model's own setup has no library entry at hand, so its engine, flags and image
  are null. A start that failed before its setup was chosen (a download, placement, a pause) leaves none.
- A run that worked here and kept its setup's id is `setup:<id>`, like the recipe setup itself (its flags and image tell
  them apart); any other is `proven`, with no key of its own.
- `recall` shows lessons (G3), but `forget_memory` doesn't take a lesson's id yet.
- Passed over while another setup is left, a recipe setup is asked for by name (`setup`); a run that worked here before
  has no name to give in chat, so it is tried again only when its image, its Sparks or its start code change.
- `recordLesson` isn't on `START_CODE`: listed there, the start code would show as a caller of the lessons' writer in
  `docs/registry.md`. A change to how lessons count changes what a start passes over with no new start version.
- A start that a power-on runs for its asker (`powerThen`) has no start code on its job, so its lessons pass nothing over.
