# R69

## Rule

**R69.** Sparkie's own code (design C 2.5, step 8): `propose_update {do: start, send, drop}` (in `updates`; its word
kinds `code` and `cancel`) proposes a change to Spark Console's own code as a pull request, all by code. It is refused
inside `runAction` for everyone until the coding trial has a pass on record for the brain in use (R67's `trialPassed`,
its sentence quoted) and the piece is turned on (`SELF_CHANGE_ON`); then only in the owner's own chat (Sparkie on the owner's own words, or the owner's button there),
never by an agent's key, `ask_sparkie`, an API call or a saved workflow's step, and from Telegram it waits for the page.
`start` fills this chat's box with `main`'s tree from Spark 2's copy of the repository and nothing else, and notes that
commit; it is refused while a proposal is open or the box holds other work. `send` reads the box back entry by entry
as data, never run; builds the proposal's tree itself on the noted commit; rebuilds the generated files with the
installed build's own generator (its `tools/`, never the proposal's, reading the proposal's sources) and refuses a
generated file in the box that isn't what that generator makes; refuses any path under `.github/`, any `.gitattributes`,
a test run's lock or map (`service/workflows.lock.json`, `test/affected-map.json`), any name that isn't plain (letters, digits, `._/+@-`; no link, no `.` or `..`) and any name that differs only in case
or Unicode form from one in the tree (every list is matched without case); lists the protected paths (the ones that always run the
whole suite, all of `tools/` among them; the parts that hold or feed the gates: this one, `20-danger`, `21-brain-rail`,
`21-updates`, `21-guard`, `21-runner`, the ladder, the sorter, `run`, `write_file`, root, the net, the hub, the box,
the trial, the eval, the brain check and each part whose Area is safety or ways in or that raises an ask; `public/`; the test helpers; and `AGENTS.md`, `docs/architecture.md`,
`docs/contract.md`), every removed or edited line of an existing test, and each existing test file it changes with
its added lines and what they change (a skip, todo or only, `process.exit`, a top-level return, a timeout); commits;
pushes `sparkie/<id>`; and opens the pull request. Sent again, it adds a commit to the same branch; with nothing
changed since, it sends that commit again (a send cut off before GitHub had it, or before its pull request). A send in
a request that read outside text is a button. `drop` closes the pull request and deletes the branch, from the chat
that started it, or from any of the owner's own chats once that chat is gone. One proposal at a time, 6 pushes
each; it is known from the copy's refs (`refs/sparkie/<id>`, `refs/sparkie-base/<id>`, `refs/sparkie-chat/<id>`, the
last a blob holding the chat's id, used only in a chat id's shape) and from GitHub, with no state file. The title (3 to
80 characters) and why (10 to 600) are the brain's words: masked, bounded, and marked as its words wherever shown.
`check_update` answers for the open proposal (its pull request, the run on its head, the failed tests' names, the
reviews and whether each is of the head), labelled as outside text. `install` (C8d) asks the owner, as `install_update`'s
dangerous ask (R54, R58), once the pull request is open at the head Spark 2 sent and GitHub's run on that head passed;
the ask is built by code: the tree, the files it changes, the run, the protected paths, the test files it changes, and
the review of that head or "Nobody else reviewed this."; Sparkie's title is marked as its words. Its yes merges the
pull request only at the head shown and only while GitHub's `main` is the commit the proposal was made on (else
nothing is merged), and stops there: GitHub marks a tree tested only after its run on a push to `main`, so the install
is the ordinary `install_update`, with its own ask, once that tree is marked. A check skipped (the mark job, on a pull
request) or neutral is no failure; the ask needs at least one success and no failure, cancel or time-out.
Nothing of a proposal is ever run, imported, required, sourced or handed to a shell. The generator is the installed
build's own `tools/make.mjs` (whose tools import only Node's own modules and each other, pinned by a test), run as a
process of its own, which must finish (ending by itself after its last word), on
the proposal's files as data: in an empty folder of mode 0700 under the state folder's `tmp`, removed on every exit,
with the proposal's `tools/` and every link taken out, the installed `tools/` and a `package.json` of its own in their
place, a clean environment (no secrets file, no token, no state folder), a time limit and its output bounded.
Every git call on Spark 2's copy runs in an environment of its own: no system or global settings and no attributes but
the tree's (`core.attributesFile=/dev/null`, `GIT_ATTR_NOSYSTEM=1`, no `info/attributes` in the copy); the copy's own may
hold only what `git init` puts there (`[core]` and its plain keys: an include, `includeIf`, a hook, `fsmonitor`, a
filter or a URL rewrite there refuses the copy before git runs); hooks, `fsmonitor` and credential helpers off; no
prompt. The token is read from the secrets file at the moment of use, for one push or one call to GitHub, and kept in
nothing that outlives it: to that one git only in its environment (a header for `github.com`), to GitHub only in the
`Authorization` header; never in a command line, a ref name, a remote's address, the copy's settings, a log, the
journal, an error or a tool result. The push names its one refspec in full, `refs/sparkie/<id>:refs/heads/sparkie/<id>`
(or `:refs/heads/sparkie/<id>` to drop it): never `--force`, `--mirror`, `--all`, tags or a `+`; its address is the
repository `pull.sh setup` recorded, on GitHub's host, fixed in code, built again and checked before each push.

## Why

Sparkie may change its own code only as a proposal the owner can read, built and checked by code, and only once a brain
has shown in the coding trial that it can.
