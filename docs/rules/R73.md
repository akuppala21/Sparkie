# R73

## Rule

**R73.** The agent door's own handling of a tool call (`mcpDoor`; Astra's A-25, 2026-11-16). Every call is answered
within 50 seconds (`DOOR_WAIT_MS`), and one agent has at most 3 calls whose work is still running: a call keeps its
slot until its work truly ends, not when the door stops waiting for it. A slow look is answered "Try again in a
minute" (its result is cached when it lands). A call of a tool that can change something (a change, or `run` and
`write_file`: `changes`) is never told to try again: past the 50 seconds it is told it is still going, that nothing
was started twice, and how to see its result. Such a call sent again by the same agent with the same arguments (the
keys' order aside) while the first is still running, or while the operation its answer names still runs, joins the
first (`doorWork`, `doorKey`, `doorGoing`): it waits on the same work and gets the same answer, nothing runs twice,
and its audit line says `joined`. Once that work has ended, a repeat runs again and the action's own check answers. The key is the agent, the tool and the arguments, never the JSON-RPC id, which a client
starts again with each session, so keeping answers by id would hand a new session an old answer.

Not promised:
- A repeat after a first call that failed runs again (a refusal did nothing).
- A repeat after the first's work has ended (or a call with no operation, like `save_file` or `remember`, once it
  answered) runs again, answered by each change's own check: a start already running says `already`; a stop of one
  not running, a restart of one running and a line already kept say `already`; `save_file` never replaces a file; a
  self-test or a compare of the same workflow already running is refused; `run_workflow` starts another run.
- Exactly once across a restart of Spark Console: what the door holds is in memory and goes. A change that began has a
  start line in the journal, and a restart marks one with no end as cut off (R43). Before calling again after a
  restart, an agent looks: `recall {kind: "call"}` shows its own calls and how each ended, or that it was cut off, and
  `recent_operations` and `fleet_events` what an operation did.

## Why

A client that hears nothing in time sends the call again. The second must not stop, start or save anything twice.

## Today

Contract 4.4 says the request id is what keeps a retry from running a change twice; the door keys on the agent, the
tool and the arguments instead (an id restarts with each client session). An agent's own `run` or `write_file` change
never runs inside the door's call today: the ladder asks the owner (R61).
