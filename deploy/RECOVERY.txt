Spark Console: what to do when it doesn't answer

This file is ~/.local/share/spark-console/RECOVERY.txt on the hub (the Spark that runs Spark Console; deploy/hub.env
names it). Every install writes it again. Run these there, in a terminal, signed in as the user Spark Console runs as.
None needs sudo. None touches SSH, Tailscale, the firewall, users or any model.

1. Go back to the build from before the last update. People, chats and settings stay as they are.
     bash ~/.local/share/spark-console/go-back.sh

2. Restart Spark Console as it is.
     systemctl --user restart spark-console-api

3. See why it stopped.
     journalctl --user -u spark-console-api -n 80 --no-pager

4. Check that it answers. A good answer starts with {"ok":true
     curl -s --unix-socket ~/.local/state/spark-console/api.sock http://localhost/health

5. Install the newest tested build from GitHub (once pull.sh setup has run). check names it; install takes its tree.
   When Spark Console doesn't answer, install asks here before it goes on without a way back: answer y.
     bash ~/.local/share/spark-console/pull.sh check

6. An update from GitHub that was cut off puts the build from before back by itself within 30 minutes. To do it now:
     bash ~/.local/share/spark-console/update-guard/update-guard.sh put-back hand
   If it says the build from before couldn't be put back whole (a full disk), nothing of it was lost: its copy is kept
   and the way back stays armed. Make room (df -h ~ shows how much is free), then run the same line again.
   While it stays armed every install waits. If it can never go back (a file of the copy that can't be read), give
   the way back up and keep the build that runs now (the build from before is then only in a snapshot, step 1):
     bash ~/.local/share/spark-console/update-guard/update-guard.sh disarm

If the page loads but Sparkie doesn't answer, type one of these alone in your own chat on the page.
Code answers them, not Sparkie's model:
     /status    /pause    /restart sparkie    /undo update    /help

Putting state back too (restore.sh --with-state in a release below, or a copy): when Spark Console says so, open it
once on your tailnet, look at what came back and press "Keep these"; until then sign-in from the internet is refused.
For an older copy or release, stop the service before putting state back. Do not run its old restore.sh --with-state
unchanged: it restarts the service itself. First update that script to skip and remove saved-runs.json and
saved-runs.json.prev, or restore by hand without them. Remove both from ~/.local/state/spark-console before restarting.
They can hold old authority to stop current workloads. The exact archive commands are in REBUILD.txt.
If your Tailscale login changed since that copy, put today's login in access.json first (yours now in place of <login>,
inside the quotes):
     python3 -I -c 'import json,sys; f,l=sys.argv[1:]; d=json.load(open(f)); d["ownerLogin"]=l; json.dump(d,open(f,"w"))' \
       ~/.local/state/spark-console/access.json '<login>'

Earlier builds are kept in ~/.local/share/spark-console/releases, the newest 10. go-back.sh uses the newest one
that isn't what's installed now; run it again to go back one more build.
