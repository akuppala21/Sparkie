# Enrolled applications and models

The Sparks page, paired Telegram and the model proposal tool use the same checked operations. Select an enrolled recipe revision and an eligible compute Spark. A stop names the original start operation. Confirming a start reserves the alias and its compute Spark, wakes it through the admitted-work policy when configured, verifies its physical identity and starts the pinned Compose workload. Spark 1 handles the controller and authenticated SSH forwards.

A warming model shows an unknown result until its local HTTP model list returns the expected name. The private collector reconciles the original operation and the owner can also use **Check result**. Both inspect the same worker receipt. Opening an app or model performs a new readiness check. The signed-in public origin and model-independent recovery path belong to the reviewed installation plan.

Both definitions pin image digests. The release's worker and controller load the same canonical recipe revision. Compose creates the container without executing it. The worker saves Docker's immutable container ID before issuing a start. An exact receipt is written before stop. An explicit stop preserves the directory, model weights, compiler cache, worker receipts and container inspection data. Docker's supervised restart policy is `unless-stopped`. The owner can read bounded runtime events and exit status. HTTP query strings, raw container logs and model inputs stay out of this result.

## Prepare an installation

The permanent controller uses `service_config` to reference its private catalog and `service_relay` for the alias-to-hub-loopback ports. Use a short private directory inside the installation's state root, such as `/var/lib/sparkie/controller/relays`. The installation enumerates and verifies the catalog hash. Only the public ingress uses the separate reviewed HTTPS port. Compute workers publish only to their own loopback interface.

1. Select existing compute identities from the protected `compute.json`. Prepare a private JSON object mapping each selected Spark to its recipe names and absolute artifact or weights directories. `/var/lib/sparkie/service-artifacts` is the dedicated empty artifact directory the stager can create. An existing export directory and the GLM weights directory must already be present. Use the tested nonroot UID 1000 for the two recipes.
2. Run `service_enrollment.py --archive <candidate/workspace-worker.pyz> --compute <private/compute.json> --enrollment <approved-placements.json> --output <new-private-directory>`. The output contains `services.json`, a worker configuration for each enrolled Spark and their SHA-256 identities. The worker archive is part of the sealed candidate. Ports, commands, paths, images, account names and file digests cannot come from model/tool input.
3. Include `services.json`, the relay ports, worker files, candidate archive and data directories in the exact owner review. After authorization, install each worker using the packaged `service_worker_stage.py` with the reviewed archive/config files, their SHA-256 values and the enrolled account. It stages content-addressed executable/configuration paths and preserves private worker state under `/var/lib/sparkie/services`. An existing data export, model environment and SSH configuration stay in place. Stage the controller catalog using the main installation's checked private-file path.
4. Verify the owner path using the actual enrolled service. For a move, verify an exact stop on the original node before starting the same alias on a newly eligible worker. Upcoming catalog changes must account for each active instance and retain its matching worker/revision until the owner stops or moves it.

## Recover a service

Check the original operation before issuing another change. A failed observation retains its reservation. An exact, newly confirmed stop can retire a previously unverified start on the same Spark and instance. The worker fences a delayed launch whose container has never started. If a container ID, protected config or physical identity changed, restore the enrolled setup and inspect the original receipt before retrying. A container disappearing from an incomplete observation does not prove it was stopped.

The controller owns the SSH master and its private control socket. Normal shutdown closes its forwards. If an unclean controller exit leaves a control socket, use the independent administrator path to check that exact socket with OpenSSH `-S … -O check` against the enrolled user and host. Stop only the verified old forward for that retired instance. Once the controller is stopped and the socket has been proved stale, retain its identity for the recovery record and remove only that stale socket before restarting the controller. A collision with a live listener requires reconciling its owner first.
