# Native launch, controlled updates and host execution

Source review of pinned Hermes v0.23.2, with focused owner-login integration
evidence below. This is preparation, not an installed service, tested cutover
or authorization for a live candidate.

## Recommended packaging

Use a sealed, versioned Hermes release directory containing the locked upstream
runtime and pinned Sparks extension. Prepare upgrades with upstream tooling in
an isolated compute checkout, then package the tested result. The live process
must not own or write that release, its dependency environment, plugin code,
service unit or release selector. Keep native chats, memory and task state in a
separate writable `HERMES_HOME`.

Run native `hermes gateway run` under systemd. Its supported generated unit
already supplies restart behavior, graceful drain, a stop budget, optional
watchdog notification and subprocess cleanup. Reuse that behavior. An
administrator-owned system unit with an unprivileged runtime user and a small
hardening drop-in is a better boundary than a model-writable user unit. Concrete
user/service/access changes belong in the eventual approved installation.

Candidate hardening includes `NoNewPrivileges`, a read-only release tree and
explicit writable state/cache/runtime paths. `ProtectSystem=strict`,
`ProtectHome` and path exceptions need qualification against the actual native
workers, SSH control sockets, user-bus access and dashboard. Do not paste a
generic hardening list and claim it works. Native restart-safe cron/Kanban workers
can use `systemd-run --user`; a drop-in on the gateway does not automatically
sandbox an independently created user service. The runtime account's filesystem
permissions must enforce the same boundary for every worker.

The model's terminal/file/Python tools operate in their compute workspace. The
gateway and private controller currently use the same trusted UID because the
broker socket is owner-only and verifies that UID. This does not provide an OS
account boundary between those trusted processes. Fleet operations remain in
the checked controller; never mount their credentials, state or socket in
model execution environments. The compute sandbox is the execution boundary.

## Native updater controls already available

`hermes_cli/update_contract.py:evaluate_update_admission` is shared by CLI and
dashboard updates. A sealed install with an `install-stamp.json` distribution
owned by a named steward is refused in-place; the supported fallback covers
custom package managers too. A `source: commit-build` stamp is also explicitly
refused. This means Sparkie can package a sealed release without patching the
native updater. Use honest provenance describing the actual package; do not
pretend a normal source checkout is a Nix or Docker installation.

Concrete proposed shape, to qualify before installation:

```text
/opt/sparkie/releases/<candidate-id>/
  hermes/                    # pinned upstream code, no .git
    install-stamp.json       # generated by the native stamp writer
    plugins/                # untouched upstream implementations
  bundled-plugins/          # full discovery collection; stock auth manifests excluded
  python/                    # qualified locked dependency runtime
  candidate.json             # artifact hashes, checks and rollback identity
/opt/sparkie/current          # protected selector for the approved release
/var/lib/sparkie/hermes/      # native mutable chats, memory and task records
```

`pm.paths.install_stamp_path` places the stamp directly in the Hermes code root.
Generate it with native `scripts.write_install_stamp.write_stamp()` using the
verified upstream commit, `base_version="0.23.2"`, `distance=0`, `source="local"`,
`distribution="sparkie"` and `update_mechanism="external"`. The CLI restricts its
distribution choices to upstream packages; the native Python writer accepts
the honest custom steward. The custom distribution
`sparkie` is handled by the supported sealed-steward fallback and refuses direct
in-place updates. `updateMechanism: external` alone is not that gate: the code
must have no `.git` and must carry the named distribution. An unstamped "unknown"
tree falls through to updater heuristics. The installed package must include
accurate provenance, not the stamp generator's fallback all-zero commit.

Keep the native dependency runtime and launcher paths valid at their installed
location; copying a development virtualenv with absolute paths is not a proven
package. A configured `HERMES_BUNDLED_PLUGINS` replaces the bundled-plugin root,
so point it at the complete protected `bundled-plugins` collection. Prepare it
with `sparkie/tools/package_plugins.py`, which copies the pinned collection,
omits stock `dashboard_auth` discovery manifests and adds the Sparks plugin.
It preserves the native auth implementations for delegation. All other native
plugin manifests remain, so the override does not discard native features.

The dashboard `/api/hermes/update` invokes that admission gate before spawning
`hermes update`. Container-managed installs have an additional refusal. These
native refusals explain why a direct update is unavailable, but they do not
implement Sparkie's candidate approval. Filesystem ownership is still needed:
an environment marker alone is not a privilege boundary.

Plugin updates have a separate route. Preserve `plugins.auto_apply: false`.
Native `--ref` pins prevent ordinary Git-plugin updates; catalog updates and
explicit repinning have their own policy. Bundle the Sparks extension into the
sealed release using `HERMES_BUNDLED_PLUGINS`, and protect all active plugin code
directories against live writes. A dashboard "update all" click must not replace
the pinned extension outside the reviewed release. Native skill learning can
remain writable; it must not be another path to host execution or authority.

The smallest promotion addition is one checked controller operation:

1. Identify the immutable candidate artifact, source diff, checks, expected
   interruption and known-good rollback.
2. Obtain exact owner approval bound to that candidate, using the existing
   Telegram/web identity and confirmation path.
3. Record the operation before switching. Gracefully drain the native gateway,
   switch the protected release selector and restart the existing service.
4. Check actual browser/API/WebSocket, Telegram ownership, local model routing
   and the changed behavior. If checks fail, restore the approved prior release
   and report what happened.

This uses systemd and upstream's runtime rather than another release service.
Keep the previous release and preserve application state. Code rollback alone
does not undo a database migration: qualification must establish backward
compatibility or an approved state restore before promotion.

## Native cron scripts are a different execution path

`cron/scheduler_script.py:_run_job_script` starts a host `subprocess.Popen`.
It restricts script paths to the active profile's `HERMES_HOME/scripts`, sanitizes
the environment and handles cancellation. It does **not** route scripts through
the selected terminal backend. The same path supports no-agent jobs and context
scripts for agent jobs. Treating `terminal.backend: spark_compute` as isolation
for these scripts would be wrong.

For the initial deployment, use native scheduled agent tasks for arbitrary user
work: their terminal/file/Python tools follow the compute backend. Keep each
active profile's host `scripts` path empty or limited to reviewed fixed scripts,
and OS-enforced read-only to the runtime, including replacement of the directory.
The runtime must not be able to create a new writable active profile that evades
that rule. A script created inside compute is a compute artifact, not an
automatically executable gateway script. A fixed reviewed dispatcher can later
submit a no-agent compute job through the checked controller if that feature is
needed; native scheduling/delivery should still own the schedule and result.

No general local-install `cron_scripts: false` setting or pluggable script-exec
backend was found in the reviewed source. `hosted_tool_policy` disables scripts
only in hosted scopes, where it also disables memory, skills and many other
required features; enabling that scope is not a drop-in solution. The supported
scheduler-provider API explicitly leaves job execution/delivery in core, so
replacing the scheduler would not fix this boundary.

Keep native `skills.inline_shell: false` (the pinned default). It prevents
`!` shell snippets in skills from becoming another host subprocess path while
retaining normal skills. Shell hooks, stdio MCP processes, plugin installs and
configured local speech/media commands likewise need reviewed host composition;
they must not acquire fleet credentials or writable live code. This review does
not qualify all those surfaces.

## Idle handling and the native reaper

The maintained terminal reaper excludes tracked foreground and background work,
then removes stale entries from its environment/activity maps **before** calling
cleanup. If `stop_idle` raises, it logs a warning but does not restore the entry.
The next tool call creates a new connection, so the private allocator must
reconcile and return the same lease. A failed cleanup never releases a durable
resource reservation.

`_suspends_when_idle` invokes `stop_idle` only for hosted sandbox keys or native
workspace keys. Normal remote gateway `session:` keys receive plain cleanup.
The Spark provider's truthful `stop_idle` method alone therefore does not provide
automatic container or Spark shutdown. Plain SSH cleanup cannot establish that
detached processes stopped; the hardware proof observed the opposite.

Hermes's supported `ctx.register_idle_task` can run a short, non-model reconciliation
callback, with native cross-process claims and status records. However, it has a
**one-hour minimum interval** and its gate measures Hermes interaction idleness,
not a compute Spark's work. It can request controller observations, but cannot
replace actual resource/process checks or satisfy an assumed shorter threshold.
For a shorter owner-selected idle threshold, reuse an existing collector cadence
or a standard systemd timer for the same checked controller scan. Do not add a
second agent scheduler. Unknown work keeps the machine awake; Spark 1 is excluded.

## Public sign-in: native Nous plus the one-owner boundary

The owner approved native Nous Portal sign-in for public browser access on
November 19. This approves authentication only; AI routing stays local. It does
not qualify a public listener or authorize a live cutover.

The native provider verifies Portal RS256 signatures, issuer, the exact
`agent:<instance>` audience, time claims and `agent_dashboard:access` scope. An
`agent_instance_id` claim, when present, must match. It maps the verified `sub` to
`Session.user_id`. **It does not compare that subject to a configured owner.**
Any token the Portal legitimately signs for that client and dashboard scope
passes local identity verification, regardless of its subject. This does not
prove another Portal user can obtain such a token: Portal's issuer-side ownership
rules determine that. The linked `nous-account-service` OAuth contract returned
GitHub 404 during this review, so those server-side rules were not independently
verified here.

No local owner-subject allowlist was found in the pinned Nous provider settings,
dashboard middleware or WebSocket gate. Authenticated Webapp users are treated
as the local machine owner by native session authority. Therefore the Sparks
extension's `OwnerBinding` alone cannot protect general native dashboard,
configuration, history and terminal features from a wrong admitted identity.

The extension now supplies a small `OwnerNousProvider` subclass of the native
`NousDashboardAuthProvider` in `sparkie_sparks/owner_login.py`:

- Delegate authorization redirects, PKCE, token exchange, JWT/JWKS verification,
  refresh and logout to Nous. Add no OAuth implementation or token parser.
- Pin the exact owner subject from trusted enrollment, alongside the native
  issuer/client. Check the returned verified `Session.user_id` after
  `complete_login`, `refresh_session` and `verify_session`. A wrong subject is
  rejected using the native method's failure convention; an unset owner fails
  closed. Do not enroll the first anonymous browser that reaches the page.
- Register through `ctx.register_dashboard_auth_provider` with the distinct
  `sparkie-owner` name. Native session construction uses `self.name`, so native
  callbacks, provider cookies and refresh retain this identity. The preparation
  profile explicitly disables stock `dashboard_auth/nous`, `basic`, `self_hosted`
  and `session_token` registrations. Their code is not patched; the Nous class
  is imported and delegated to. Do not rely on load order. The token-only
  `drain` maintenance provider is also unprovisioned until a separately scoped
  maintenance credential is qualified; it is not an interactive sign-in route.
  The protected bundle also excludes these discovery manifests for every
  profile. A launch-profile deny-list alone is insufficient: independent review
  reproduced a secondary profile's stock Nous plugin replacing the process-wide
  listener callback before native context rejects its direct registration.
- Native Web Access's `dashboard_auth.listener_client.offer/use` hook constructs
  the same owner-filtered subclass with its own registered client. A plugin
  reload retains that client and the owner check. Closing the listener restores
  its configured client from current settings, even after reload; it never
  revives a revoked owner or overwrites an unrelated replacement. Removing
  required setup on launch-profile reload removes the prior provider.
- The extension checks native launch scope before offering its global callback
  or removing a registration. An incomplete secondary profile cannot revoke
  the launch profile's sign-in, including when the client is configured only in
  the launch profile's YAML rather than a global environment variable.
- `SPARKIE_WEB_OWNER_SUBJECT` holds the exact, verified owner subject in protected
  launch configuration. This setting, the native client/issuer and provider
  enable/disable policy must be protected from runtime/model writes. It is not a
  model prompt, a user-editable profile preference or first-visitor enrollment.

This wrapper enforces authorization at the common native sign-in seam:
HTTP cookie and bearer admission, token verification for WebSockets, and the
authenticated endpoints issuing short-lived socket tickets. A check in the
Sparks router alone is insufficient. The final focused Spark 4 run passed 65 checks
in 7.97 seconds: 52 owner-auth/package scenarios across both native dashboard and
Webapp, plus native configuration and registration smoke. These used real native routes,
RSA JWT verification, PKCE/cookies/refresh, native-app bearer enrollment and actual
WebSocket handshakes with an isolated fixture issuer. No real Portal account,
public tunnel or installed sign-in was changed. Initial fixture failures are
retained in `docs/review-astra/evidence/hermes-owner-login-2026-11-19/`.

The packaged bundle and its launch environment must be administrator-owned and
read-only to the runtime. Per-profile user-plugin roots must not let model work
introduce executable plugins; project-plugin discovery remains disabled. Native
plugin administration installs trusted code, so an owner-initiated install is an
explicit trusted action, not authority conferred by a model-generated plan. The
bundle alone cannot stop arbitrary code already allowed to execute in the host
process. Final OS permission and trusted-install checks remain packaging gates.

The Webapp additionally binds browser cookies to its local browser credential;
bare browser JWTs cannot be reused as independent bearers. Native-app sign-in
uses its maintained RFC 8252 flow before those tokens work independently. These
checks remain native, with the owner filter applied afterward. Ordinary logout
and browser sign-out retain the limits described below.

Native enrollment is available through `hermes dashboard register` or Portal's
Local Dashboards page. The CLI registers a self-hosted client with the current
Nous account and the exact callback URI. Gateway Web Access registers a separate
client under `webapp/sign-in-registration.json`, retaining the standalone
dashboard's callback. Configure the correct `dashboard.public_url` or
`webapp.public_url`: a public URL engages authentication even behind a loopback
reverse proxy. Also verify HTTPS cookie handling and the actual proxy trust
configuration. A bare unconfigured loopback listener must never be publicly
forwarded.

Enrollment must derive the owner subject from the owner's verified native Nous
session, not from an email guess, decoded unsigned token, chat message or the
first public login. Use the supported native registration/sign-in in an isolated
operator-only loopback session, reached through the existing authenticated
operator path while public serving remains closed. After the owner signs in,
read native `/api/auth/me`'s verified `user_id` and bind it with the exact client
and issuer in administrator-owned launch settings. The owner never needs to
paste a token into chat. Present those enrollment and recovery steps with the
concrete cutover approval. This operator procedure and actual Portal account
recovery still need real-path qualification; no bootstrap service is added.

The parent review observed an existing server-side Tailscale Funnel route on
Spark 1 at `https://hub.example.invalid:8443/`. The proposed cutover can reuse
that address, with the native callback at `/auth/callback`, after authentication
is qualified. A viewing device needs only its browser and Nous sign-in, not a
Tailscale client. Save the existing `8443` route configuration for rollback;
switching it is part of the approved live candidate. The separate `443` route
for `unrelated.example.invalid` to port `8100` belongs to another app and must stay
untouched. These are proposed routing instructions, not a changed live route.

Recovery can use an existing protected operator SSH/local CLI path, independent
of inference and Portal availability, to stop public serving, repair the protected
configuration and restart the native service. Preserve that route throughout
cutover. Native `hermes webapp --sign-out` rotates its browser binding and closes
bound browser sockets; it deliberately leaves native-app sign-ins intact.
Nous `revoke_session` itself is a no-op: ordinary logout clears browser cookies,
and does not prove a copied refresh token was revoked at Portal. Portal documents
dashboard-client revocation in Local Dashboards, but its immediate token effect
needs a real qualification. Do not claim offline browser recovery, universal
token revocation or restoration of a lost Portal account from this source review.

Before public exposure, repeat the affected integration checks on the sealed
candidate and qualify the real owner sign-in, proxy/public URL, operator recovery
and Portal revocation behavior. The fixture checks do not establish those live
properties. The packaged native dashboard must report the verified upstream
version and candidate identity; a development `vunknown` display is not release
provenance. Use the native sealed-install stamping described above.

## Checks for the future packaged candidate

These are selected upstream checks to run on a compute Spark when packaging is
implemented; none is claimed as run by this source review:

- `tests/scripts/test_write_install_stamp.py`,
  `tests/hermes_cli/test_steward_detection.py` and
  `tests/hermes_cli/test_update_contract.py`: stamp identity, sealed-tree
  classification and refusal. Add one small assembled-package check for the
  actual `sparkie` distribution and both CLI/dashboard update entry points.
- `tests/hermes_cli/test_web_server_update_status.py`,
  `tests/hermes_cli/test_plugins_auto_update.py` and
  `tests/hermes_cli/test_plugins_auto_update_boundary.py`: native UI status and
  plugin pins. Also prove the packaged extension cannot be replaced by either
  native plugin update route or an unprivileged direct file write.
- `tests/hermes_cli/test_systemd_watchdog_unit.py` and
  `tests/gateway/test_systemd_watchdog_lifecycle.py`: native unit/watchdog
  behavior. The actual hardened unit still needs a disposable compute-host
  startup, drain, worker, restart and rollback check.
- `tests/cron/test_cron_script.py`: retain native path/cancellation behavior;
  verify the assembled service cannot write or replace host scripts and its
  scheduled agent's ordinary commands run in compute. Include inactive/new
  profile handling rather than testing only the default profile.
- `tests/hermes_cli/test_plugin_idle_tasks.py`,
  `tests/hermes_cli/test_plugin_idle_tasks_off_thread.py`,
  `tests/hermes_cli/test_plugin_idle_tasks_stop_fence.py` and
  `tests/gateway/test_plugin_idle_task_housekeeping.py` only if that maintained
  hook is selected. Independently verify the actual controller keeps resources
  held for a detached job, unknown result and failed native teardown.
- `tests/plugins/dashboard_auth/test_nous_provider.py`,
  `tests/hermes_cli/test_dashboard_auth_middleware.py`,
  `tests/hermes_cli/test_dashboard_auth_ws_auth.py`,
  `tests/hermes_cli/test_dashboard_auth_ws_tickets.py`,
  `tests/gateway/test_webapp_public_url.py` and
  `tests/gateway/test_webapp_gated_sign_out.py`: preserve the native transport,
  JWT and sign-out semantics while adding focused owner-subject cases to the
  actual configured provider stack. Portal issuance and recovery still need
  real owner-path qualification.

Then qualify the exact owner approval, promoted identity, auth and rollback
paths on the assembled candidate. Passing the upstream fixtures alone cannot
qualify the OS permissions or the complete product.
